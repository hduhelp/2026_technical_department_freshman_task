## 一、这是什么

一个校园失物招领平台：**丢东西的人**和**捡到东西的人**在这里发布信息，从而找到彼此。

它要解决的核心痛点是——**两边看不见对方**：

- 丢的人发了"求找"帖，捡到的人不知道；
- 捡的人发了"招领"帖，丢的人也不知道。

所以除了常规的关键词搜索，本项目还做了一个 **AI 智能匹配**：
发布一条帖子后，系统自动去**反向类型**的帖子里找（"丢失"↔"招领"），
用大模型判断有没有描述的是**同一件物品**，有就提醒用户。

### 5. 启动

```bash
go run .
```

看到服务监听 `127.0.0.1:8080` 后，浏览器打开：

```
http://127.0.0.1:8080/static/index.html
```

> 首次启动会自动创建 `lostfound.db`（建表）和 `uploads/` 目录，**无需手动建库**。

### 6. 试用建议

1. 打开首页 → **注册**一个账号 → **登录**
2. 点 **+ 发布**，填一条"丢失"的信息（可以上传一张图片，选完会立刻预览）
3. 再发一条"招领"的信息，描述写成**和上一条像同一件东西**的样子
4. 第二条发布成功后会自动触发 AI 匹配 → 弹出提示"似乎有人发布了相关帖子"
5. 进 **管理我的帖子** 可以展开详情、编辑、删除、改状态

## 四、技术栈

| 层 | 选择 | 为什么选它 |
|---|---|---|
| 语言 | **Go** 1.25 | 二面岗位要求 |
| Web 框架 | **Gin** | 轻量，路由和中间件的写法清晰 |
| 数据库 | **SQLite**（`modernc.org/sqlite`） | **纯 Go，免 cgo** —— Windows 上不用装 MinGW-w64 |
| 认证 | **JWT**（HS256，24 小时） | 无状态，重启服务后旧 token 仍然有效 |
| 密码 | **bcrypt** | 自带随机盐 + 可调 cost，不用 MD5/SHA |
| 大模型 | **DeepSeek**（`deepseek-v4-flash`，OpenAI 兼容格式） | 便宜够用；换成别家只需改 base_url 和 model |
| 前端 | **原生 HTML / CSS / JS** | 不引框架，零依赖，直接由 Go 托管 |

## 六、设计说明

### 1. 数据模型：为什么只有两张表

`users`（谁）+ `items`（什么东西）。失物和招领**共用一张表**，用 `type` 字段区分 ——
两者的字段完全一致，拆成两张表只会让查询和代码重复。

> 如果以后要多图，需要新增 `item_images`（一对多：外键放"多"的那边）；
> 要做收藏，需要新增 `favorites(user_id, item_id)`（多对多：必须用中间表）。

### 2. 图片上传的四个坑

用户上传文件是**危险操作**，因为文件名是客户端给的。实现的四条防护：

| # | 措施 | 不做的后果 |
|---|---|---|
| 1 | **文件名由服务端生成**（纳秒时间戳 + 原后缀） | 客户端传 `../../main.go` → **路径穿越，可覆盖服务端任意文件** |
| 2 | 限制 **5MB** | 有人上传超大文件占满磁盘 |
| 3 | **后缀白名单**（jpg/jpeg/png/gif/webp） | 上传可执行文件 / 脚本 |
| 4 | 上传目录与静态目录**分离**（`/uploads` vs `/static`） | 上传目录被当成静态资源执行 |

★ 第 1 条是关键：**"写文件"比"读文件"危险** —— 同一类漏洞，写权限更大。
（这个问题在我之前的 Web 学习作业里以"路径穿越"的形式出现过，那次是**读**文件。）

### 3. AI 匹配的三个取舍

**① 不做关键词检索，而是把候选帖全文交给模型。**

中文里"折叠伞"和"雨伞"、"七教"和"七教北"靠关键词匹配不到；
而且让模型先"提取关键词"会丢掉描述性细节（比如"伞柄有蓝色贴纸"—— 恰恰是能匹配上的证据）。
数据量小的时候（<100 条），全文交给模型**更准，而且只要一次调用**。

**② 一次请求打包所有候选，而不是一条帖调一次。**

20 个候选 → 1 次调用（而不是 20 次），成本和延迟都降一个数量级。

**③ 结果分三档（same / maybe / no），不用百分比。**

大模型自报的"置信度 90%"是它编的，不是真实概率；而"是 / 可能是 / 不是"这种分档很稳定。
还要求它在 `reason` 里**引用原文中的具体字词** —— 这样它是不是在"糊"一眼就能看出来。

**④ 失败降级。**

模型调用失败 / 解析失败 / 没有候选 → 一律返回 `{"ok": true, "result": []}`，**不返回 5xx**。
理由：发布帖子这个主流程已经成功了，附加功能故障不该让用户以为发布失败。失败原因写日志。

### 4. 安全设计

完整清单见 `API.md` 第四节，几条主要措施：

- 密码用 **bcrypt** 哈希，数据库里永远不是明文；
- 所有 SQL 都走**参数化查询**（`?` 占位符），值永不拼进语句；
- `ORDER BY` 的方向**无法参数化** → 用**白名单**（只接受 `asc` / `desc`）；
- 修改 / 删除 / 改状态 / AI 匹配**全部校验"是不是发布者本人"**；
- 列表接口**不返回联系方式**，只有详情才返回；
- 登录失败统一返回"用户名或密码错误"，**防止枚举用户名**；
- **不信任客户端**：`item_id` / `publisher` / `user_id` / `status` / `created_at` / 图片文件名，一律服务端决定。

## 七、已知限制

- **退出登录在前端完成**（清除 `localStorage`）。JWT 是无状态的，服务端不维护会话 ——
  代价是 token 在 24 小时内**无法被服务端主动吊销**。
- SQLite 是单文件存储，适合单机演示；高并发写入场景需要换服务型数据库。
- AI 匹配依赖外部模型 API：有网络 / 额度依赖；候选集只取**最近 20 条**反向帖。
- 图片存在本地 `./uploads/`，未做压缩 / CDN；**每条帖只支持一张图**。
- 匹配结果目前只提示**发帖人**，没有通知被匹配到的另一方。
- 未实现"注销账号"和"找回密码"。

## 八、后续可以做的事

- 匹配召回升级为**两阶段**：地点 / 时间 / 类别宽松召回 → 模型精判（recall → rerank）
- 匹配结果通知**双方**（丢的人和捡的人都收到提示）
- 图片多图支持 + 压缩 + 上传进度条
- 用 `migrations/001_init.sql` 之类的**迁移文件**管理表结构变更
- 接口加上限流（`/upload` 和 `/items/:id/match` 是资源消耗点）
