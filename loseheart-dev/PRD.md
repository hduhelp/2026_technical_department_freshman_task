# 杭州电子科技大学校园失物招领平台 PRD

版本：v2.5，MVP 需求稿  
日期：2026-10-04

本文记录已确认的 MVP 产品需求。演示阶段使用模拟校园账号，不假定已有学校认证接口或校方授权。校区选项按用户指定设置。

## 1. 产品目标

为校园里的失主与拾主提供统一的发布、搜索和联系入口，让用户完成“发布信息—发现线索—通过帖子联系方式核实—约定归还—标记完成”的流程。

帖子采用社区卡片形式，保留结构化的物品、地点、时间与描述字段，便于搜索。首版围绕失物归还，不加入与归还无关的关注、积分或热榜。

## 2. 已明确的需求

- 用户端包含网页与微信小程序，另有后台管理端。
- 用户能够发布寻物帖和拾物帖，发布时必须明确选择类型。
- 用户能够浏览、搜索帖子并联系发布者。
- 后台支持帖子审核、违规处置与举报处理。
- MVP 不接入 AI，仅在发布前人工审核；举报后由管理员再次处理。
- 未来接入 AI 时，再采用“AI 初审通过后发布—人工复审”的两阶段流程。
- 发帖必须提供至少一种联系方式（微信号、手机号等），用户通过该联系方式在平台外核实与协商归还。
- 无统一存放点，不建设存放点管理模块。
- 演示阶段数据持久保留，不建设自动过期、定期清理或用户物理删除功能。撤回、下架仅改变可见状态。
- 仅杭电师生使用，身份验证后才能浏览和发帖。
- 首阶段用于演示，之后争取校园试运行。
- 网页与微信小程序同时交付，共享账号、帖子、通知与审核状态。

## 3. 用户与权限

| 角色 | 主要权限 |
| --- | --- |
| 访客 / 未验证用户 | 仅访问平台介绍、登录与身份验证入口，不能浏览帖子或发帖 |
| 已验证杭电师生 | 发布、搜索、管理自己的帖子，查看联系方式、举报 |
| 管理员 | MVP 只设一种管理员角色：审核帖子、处理举报、下架违规内容、禁用账号、重置演示账号密码、查看操作记录 |

演示阶段使用预置的模拟学号 / 职工号和平台密码登录，不接入学校真实数据。账号代表模拟师生身份，不能声称已完成真实校园认证。演示账号由项目成员预置，不开放通过任意填写学号即可获得师生身份的自助注册。密码须以安全哈希保存，不保存明文。忘记密码由演示管理员重置。网页与小程序共享同一平台账号、帖子和通知；首版增加微信绑定与小程序快捷登录（方案 B）。

## 4. 核心使用流程

### 4.1 寻物

用户选择“寻物” → 填写物品、丢失地点、时间、特征和联系方式 → 提交审核 → 通过后公开 → 浏览拾物帖或收到联系 → 核实物品 → 约定归还 → 标记“已找回”。

### 4.2 拾物

用户选择“拾物” → 填写物品、拾获地点、时间、描述和联系方式 → 提交审核 → 通过后公开 → 通过帖子联系方式收到认领 → 使用未公开的特征核实 → 归还 → 标记“已归还”。

无统一存放点，由双方自行协商归还地点。若拾主自行交存，可在描述中注明位置，不增加存放点字段或管理模块。

### 4.3 举报

用户选择举报对象与原因 → 平台生成举报记录 → 管理员查看相关内容和历史处置 → 驳回举报、下架帖子或禁用账号 → 向举报者反馈处理结果。举报原因包括虚假信息、不良内容、隐私泄露、骚扰、其他；管理员处置必须填写原因。重复举报可以合并，但不得只因举报数量多就自动认定违规。

## 5. 帖子字段

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 帖子类型 | 是 | 寻物 / 拾物，必须主动选择 |
| 物品名称 | 是 | 如校园卡、耳机、雨伞；列表标题可由类型与名称生成 |
| 校区 | 是 | 必须选择下沙校区、绍兴校区、文一校区之一 |
| 地点 | 是 | 用户自由填写具体地点，最多 100 字 |
| 丢失 / 拾获时间 | 是 | 标签随类型变化；允许“仅知道日期”“大致时间段”，不强迫用户编造分钟 |
| 物品描述 | 是 | 颜色、外观、特征等，最多 300 字 |
| 图片 | 否 | 最多 6 张，每张不超过 5 MB，支持 JPEG / PNG；不支持动图、视频与任意文件 |
| 补充信息 | 否 | 品牌、附件、经过等并入描述填写，共用 300 字上限 |
| 联系方式 | 是 | 至少填写一种，类型为微信 / 手机号 / QQ / 其他，填写对应内容；空值或纯空白不可提交；仅已验证登录用户可在详情页查看并复制，列表不展示，提交时提示可见范围 |

MVP 不设物品分类字段或物品分类筛选，由用户在物品名称和描述中自行说明，支持关键词搜索。

校园卡和证件图片需提醒遮挡完整学号、证件号码等信息。拾物帖应保留部分特征供联系后核实，避免公开全部认领依据。

## 6. 页面与功能范围

| 页面 / 模块 | 首版功能 |
| --- | --- |
| 首页与搜索 | 寻物 / 拾物切换；关键词搜索，以及校区、时间和完成状态筛选；默认展示未完成帖子 |
| 帖子详情 | 图片、结构化信息、发布者昵称和头像（不公开完整学号 / 职工号）、状态、联系方式与举报入口 |
| 发布 / 编辑 | 类型选择、必填检查、提交反馈、审核结果与修改后重审 |
| 我的 | 我的帖子、审核状态、修改、撤回、标记完成、通知 |
| 管理后台 | 发布前人工审核队列、举报队列、账号处置、演示账号密码重置、操作记录 |

站内通知和未读提示覆盖审核结果与帖子举报处理结果，放在“我的”页面，不设置独立消息页；MVP 不做微信订阅提醒。

## 7. 联系与归还规则

- 发帖必须提供至少一种联系方式，不能仅在描述中提及联系而跳过必填字段。寻物帖与拾物帖执行相同规则。
- 已验证登录用户在帖子详情查看联系方式，自行通过微信、电话等渠道联系发布者，核实物品并协商归还；平台不提供聊天、会话、好友或拉黑功能。
- 联系方式作为帖子内容接受人工审核；修改联系方式后按帖子编辑规则隐藏并重审。
- 发布者手动标记“已找回 / 已归还”，允许纠正误操作；平台不把外部联系行为等同于归还完成。
- 不引入正式认领申请、凭证审批和双人确认流程。若试运行出现冒领或归还争议，再讨论是否增加。

## 8. 审核机制

MVP：提交帖子 → 待审核（其他用户不可见）→ 管理员审核文字、图片和公开联系方式 → 通过后公开 / 退回修改 / 拒绝。发布后不要求每篇帖子再审核一次；管理员可因举报或发现违规而下架。

审核状态与物品处理状态分开记录：

- 审核：待审核、通过、退回修改、拒绝、下架。
- 物品处理：寻找中 / 待认领、已找回 / 已归还、已撤回。

公开内容编辑后须重新审核。首版编辑提交后先隐藏帖子，重审通过再公开，避免新内容绕过审核。标记完成无需内容重审。

退回、拒绝或下架须说明原因；发布者可修改后重新提交。演示阶段由项目成员承担审核，通过人工操作演示审核结果，不承诺固定处理时限。MVP 只设一种管理员角色。禁用账号后禁止登录且已有登录态不能继续使用；其已有帖子隐藏，帖子及审核、举报记录保留。

未来版本：引入 AI 初审，通过后发布，再由人工复审。该流程暂不纳入 MVP 的界面、开发和验收；AI 异常处理与自动发布规则届时讨论。

## 9. 通知与异常情况

- 审核通过、退回、拒绝和下架时通知发布者，给出必要原因。
- 提交失败保留表单内容；重复点击不生成重复帖子。
- 已完成帖子保留完成标记，并可通过筛选查找，避免继续按未完成帖子展示。
- 帖子隐藏、撤回或下架后，其他普通用户不能通过详情或接口读取帖子及联系方式；已在平台外建立的联系不受平台控制。
- 管理操作需记录操作者、对象、动作、原因与时间。

## 10. 首版验收标准

1. 未选择类型或缺少必填字段时无法提交；寻物与拾物的地点、时间标签语义正确。
2. 未验证用户不能通过列表、搜索、直接链接或接口读取帖子；待审核、拒绝、隐藏及下架帖子仅允许发布者和有权限的管理员查看。
3. 帖子发布前必须人工审核通过；后台记录审核人、时间与结果，MVP 不产生常规发布后复审任务。
4. 修改公开内容后必须重新审核，未通过的修改不会公开。
5. 用户能通过关键词搜索及帖子类型、校区、时间和状态条件找到帖子；不提供物品分类筛选。
6. 寻物帖与拾物帖均必须提供至少一种联系方式，类型为微信 / 手机号 / QQ / 其他；缺少、空值或纯空白时无法提交；已验证登录用户可在通过审核的帖子详情查看并复制，列表不展示，未验证用户无法通过接口读取。
7. 帖子举报能进入后台并完成处置；普通用户不能访问后台或管理他人帖子。
8. 发布者标记完成后，帖子在列表与详情中的状态一致。
9. 网页与小程序同时交付，同一账号的帖子、通知和状态保持一致；完成从网页发帖、小程序查看联系方式到标记完成的跨端演示。
10. 模拟师生账号能凭学号 / 职工号与平台密码登录；服务重启后帖子、图片、通知和审核记录仍可访问。
11. 描述超过 300 字时无法提交，补充信息不能绕过上限。
12. 小程序绑定已有平台账号后，可通过微信快捷登录，并看到网页端的帖子和通知。
13. 按北京时间自然日计数，同一账号当天跨端成功提交 3 篇新帖进入审核后，第 4 篇新帖被拒绝；次日零点恢复额度；寻物与拾物合并计算，失败、重复请求、修改及重新提交已有帖不额外扣减，拒绝或撤回不返还额度。
14. 日期未填、时间在未来或时间段起止颠倒时无法提交；只填日期的有效帖子可提交。
15. 帖子超过 6 张图片、单图超过 5 MB 或格式不符时被拒绝；符合限制的图片可上传并持久保存。
16. 物品名称超过 50 字、地点超过 100 字或必填文本为纯空白时无法提交；前后端校验规则一致。

17. 校区必填且仅接受下沙校区、绍兴校区、文一校区；具体地点自由填写；未选择校区或提交其他值时无法发帖。
18. 公开帖子修改提交后隐藏，重审通过再展示；标记完成及撤销误操作无需内容审核。
19. 禁用账号后不能登录或继续使用已有登录态，已有帖子不再对普通用户展示，帖子及审核、举报记录仍保留。
20. 管理员处理举报须填写原因；演示账号密码可由管理员重置；更换微信绑定须先验证平台密码并遵守一对一绑定限制。
21. 发布者资料展示昵称和头像，不公开完整学号 / 职工号；审核与帖子举报处理提供站内通知及未读提示。

22. 图片由帖子 images JSON 数组保存，默认空数组，最多 6 个不重复的 Object Key，数组顺序决定展示顺序和封面；修改数组触发重审，审核快照保留旧版本，禁止跨用户引用图片。图片存储在私有 OSS Bucket go-lost-found；上传、读取均经过 Go 后端校验权限；未验证用户或无权访问所属帖子的用户不能通过图片接口读取，前端不包含 OSS 密钥或 OSS 签名 URL。

23. JWT 签发后 24 小时过期，过期请求返回未登录状态；JWT 携带用户登录版本号，每次请求与用户表比对。退出成功后该账号网页、小程序及管理员端的全部旧 JWT 失效；禁用账号或修改/重置密码同样递增版本，未过期 JWT 不能绕过版本或禁用检查。旧版本退出请求重试不能递增新版本，避免使后续重新登录的令牌失效。

24. 密码以 Argon2id 哈希保存，每条密码记录使用独立随机盐和已确认参数；相同密码不会生成相同记录，错误密码无法登录；数据库和日志不暴露明文密码；接口仅允许管理员重置成功时一次性返回随机临时密码。
25. 密码长度为 8–32 个字符，允许空格及 Unicode；超限拒绝，不截断或自动去除空格；修改密码验证原密码，密码更新与登录版本递增在同一事务内完成，使全部旧 JWT 失效。
26. 管理员重置密码后全部旧 JWT 失效，临时密码首次登录仅允许修改密码或退出；成功修改后重新登录才能访问业务功能。
27. 账号不存在或密码错误时使用统一提示；同一账号 10 分钟内连续失败 5 次后暂停密码登录 10 分钟；账号失败计数、暂停状态及来源限速存入 Redis，验证并发计数与到期恢复生效。
28. JWT 验证固定 HS256 算法及签发方、受众、时间；网页使用 HttpOnly、SameSite Cookie 且修改类接口有 CSRF 防护，小程序使用 Bearer 请求头；图片接口执行同样的权限检查。
29. 非管理员不能通过直接接口调用审核、下架、禁用或重置密码；用户不能修改他人帖子或任意读取无权限的 OSS 对象；文件格式校验不依赖扩展名。

## 11. 观察指标

关注有效寻物 / 拾物帖子数、审核等待时间、举报处置时间和发布者标记的完成率。联系和归还在平台外进行，不统计平台无法直接观测的首次联系时间。完成率属于用户自报结果，不能直接称为实际归还率；数值目标在试运行获得基线后确定。

## 12. 演示阶段限制

本节时间、文字长度、帖子图片、发帖额度及保存规则均已确认。联系方式为必填；不包含聊天文字、聊天图片或消息发送频率限制。

| 对象 | 初始规则 | 目的 |
| --- | --- | --- |
| 丢失 / 拾获时间 | 日期必填，可选具体时间或时间段；不得晚于当前时间，时间段开始不得晚于结束；不限制追溯天数 | 避免误填未来，支持补发旧信息 |
| 物品名称、地点、描述 | 名称 1–50 字，地点 1–100 字，描述（含补充信息）1–300 字；纯空白不算有效内容 | 保证展示与提交可控 |
| 帖子图片 | 最多 6 张，每张不超过 5 MB；JPEG / PNG | 控制上传与页面加载；服务端校验格式和大小 |
| 发帖额度 | 已确认：每个账号每天最多发布 3 条帖子；按北京时间自然日计数，每日零点重置；网页与小程序、寻物与拾物合并计算，成功提交新帖进入审核即计 1 条 | 第 4 条提示次日恢复；失败、重复请求、修改及重新提交已有帖不额外扣减；拒绝或撤回不返还额度 |
| 保存期限 | 不自动过期，持久保存；撤回与下架不物理删除 | 满足演示阶段要求 |

图片文件与数据库记录都须持久保存，不能只保存临时上传地址。以上限制属于本产品规则，不代表微信平台限制。发帖额度须由服务端统一执行，防止并发提交超额；同一提交请求重试不能重复创建帖子或扣减额度。前后端执行一致的校验，超限提示具体原因。

## 13. 跨端账号方案 B（已确认）

以平台账号作为统一身份：一个模拟学号 / 职工号对应一个用户。网页使用账号密码登录；小程序首次登录平台账号后主动绑定微信，后续可使用微信快捷登录。两端共享同一份帖子、通知和每日发帖额度。

微信绑定流程：用户先成功登录平台账号，再主动绑定微信身份；此后小程序通过已绑定身份找到平台账号。不得只凭用户提交的学号进行绑定。一个平台账号最多绑定一个微信身份，一个微信身份最多绑定一个平台账号。更换绑定前必须验证平台密码；新绑定成功后旧绑定失效，绑定失败则保留旧绑定。

微信绑定是登录便利功能，不是学校身份认证。首版包含微信绑定、验证平台密码后换绑与小程序快捷登录，不提供单独解绑入口；网页微信扫码登录不在当前范围。演示学校身份仍使用模拟数据；微信登录需具备小程序配置条件，模拟微信流程不能标为真实绑定已验证。

## 17. 后端技术选型（已确认）

本节技术组合及登录规则已确认，JWT 有效期为签发后 24 小时。

| 项目 | 已确认选择 | 与本项目需求的关系 |
| --- | --- | --- |
| HTTP 框架 | Gin | 组织 API 路由、参数验证与认证中间件 |
| 数据库访问 | GORM + MySQL 驱动 | 常规数据操作使用现成库；额度和审核状态变更显式使用事务 |
| 登录凭证 | JWT，使用 golang-jwt/jwt/v5 | 平台账号密码登录和微信绑定登录最终使用同一套平台身份 |
| 登录失效控制 | JWT + 用户表 token_version | JWT 携带用户 ID、登录版本与有效期；每次请求验证 JWT 并查询用户实时状态、权限和版本。退出、密码修改/重置、禁用账号递增版本，使该账号所有端的旧令牌失效；不保存独立登录会话 |
| JWT 有效期 | 签发后 24 小时，过期重新登录 | MVP 不增加刷新令牌或滑动续期流程；网页、小程序及管理员适用同一有效期 |
| Redis | MVP 引入，用于登录限制 | 保存账号登录失败计数、暂停登录状态及来源请求限速，按窗口自动过期；用户登录版本与每日发帖额度仍使用 MySQL |

本项目使用 JWT 作为登录凭证，密码验证和微信凭证验证仍由后端执行。账号密码或微信凭证验证成功后才签发平台 JWT；签名校验通过仍须检查实时账号权限，不能只信任令牌里的管理员角色。Token 不包含密码、OSS 密钥或公开联系方式；普通签名 JWT 不加密载荷。

每日发帖限制：在同一 MySQL 事务中锁定该用户的配额记录（或使用条件更新），检查北京时间当日成功提交数量并插入帖子；失败回滚，防止并发第 4 篇提交绕过限制。已有帖修改不参与新帖计数，不依赖 Redis 清理时间或定时零点任务。实现时仍需满足同一提交重试不重复扣额的验收要求。

网页通过 HttpOnly、SameSite=Lax Cookie 传递 JWT，不写入 localStorage；小程序通过 Bearer 请求头调用 JSON、上传及图片下载接口。图片认证加载仍需联调验证。

登录失效规则：用户表 token_version 初始为 1，登录成功时读取并写入 JWT；正常登录不递增。退出采用按用户 ID 和当前令牌版本的条件递增，成功后清除客户端凭证；任何一端退出会使该账号所有端的旧 JWT 失效。密码修改/重置、禁用在同一事务内更新相关用户字段并递增版本。登录签发与这些更新协调用户行锁，避免旧密码签发新版本令牌。版本每次认证实时读取，不缓存旧值。网页端 CSRF 防护继续保留，不依赖已删除的会话表，具体机制为同源代理、Origin/Referer 校验及 HMAC 签名双提交 CSRF；登录后 CSRF 值绑定 JWT 的随机 jti，不保存会话。

参考：[JWT 验证](https://golang-jwt.github.io/jwt/usage/parse/)、[JWT 签名与载荷](https://golang-jwt.github.io/jwt/usage/signing_methods/)、[MySQL 锁定读](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)、[Gin 参数绑定](https://gin-gonic.com/en/docs/binding/binding-and-validation/)、[GORM 文档](https://gorm.io/docs/)。

## 18. 密码、认证与权限细则（已确认）

1. 密码保存采用 Argon2id 单向哈希，每个密码生成独立随机盐，使用成熟实现，不自创加密算法。初始参数为内存 19 MiB、迭代 2 次、并行度 1；数据库保存算法、参数、盐和哈希，不保存明文或可还原的密码。实现时验证本机开销。
2. 密码长度为 8–32 个字符，允许空格与 Unicode，不强制大小写、数字和符号组合，不截断或自动去除空格。密码不能出现在日志与操作记录中；接口唯一例外为管理员重置成功时向当前授权管理员一次性返回随机临时密码，不持久保存明文，不在通知中交付。
3. 用户修改密码须验证原密码；管理员重置为随机临时密码，用户下次登录后必须修改，完成前仅允许修改密码或退出。修改或重置成功后，在更新密码的同一事务内递增 token_version，使该用户所有端的旧 JWT 失效；演示预置账号亦保存哈希。
4. 登录失败统一提示“账号或密码错误”，不对外区分账号不存在。同一账号 10 分钟内连续失败 5 次，暂停密码登录 10 分钟；同时对来源请求限速，防止绕过和批量尝试。失败计数、暂停状态及来源限速使用 Redis，计数与到期设置需原子执行，暂停期内的尝试不延长暂停时间；成功密码登录重置对应账号失败计数，不清空来源限速。该限制独立于已确认的发帖额度。
5. JWT 使用 HS256，使用独立、随机生成的至少 32 字节签名密钥，不复用数据库密码、微信 AppSecret 或 OSS 凭证；验证固定算法、签发方、受众、签发时间和 24 小时有效期，并查询用户表的 token_version、账号状态及实时权限；缺少版本字段或版本不一致的令牌拒绝访问。
6. 网页端通过 HttpOnly、SameSite Cookie 携带 JWT，并验证修改类请求的来源及 CSRF 防护；非本机 HTTP 演示环境使用 HTTPS 与 Secure Cookie。小程序使用本地登录凭证并在请求头携带 Bearer Token，不放在 URL 中。两端图片请求同样须认证，具体加载流程在接口设计及联调时落实。
7. 后端执行管理员权限、帖子所有权及图片归属检查。前端隐藏按钮不等于授权；客户端提交的角色、发布者 ID 或审核状态不能作为可信权限依据。
8. 文件上传校验实际图片格式及大小，不只检查扩展名；后端按当前用户生成专属前缀下的随机 Object Key，上传成功后返回。帖子提交时校验对象属于该用户且已存在，保存有序图片数组；审核快照保留当时的数组，旧对象不覆盖。读取时由帖子或有权访问的审核记录定位图片，不允许客户端指定任意 OSS 对象进行读取。账号、帖子和图片权限规则沿用已确认需求。

参考：[OWASP 密码存储](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)、[会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)、[CSRF 防护](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。

本节规则、初始参数、密码修改及临时密码流程已确认；继续采用 JWT 24 小时有效期、用户表 token_version 及私有 OSS 后端访问方案，登录限制改用 Redis。密码校验开销、Redis 并发计数和过期恢复、两端凭证传递、CSRF 防护与图片认证需在实现后验证。

Redis 登录限制的实现依据：[Redis 计数与限速示例](https://redis.io/docs/latest/commands/incr/)、[过期时间](https://redis.io/docs/latest/commands/expire/)。Redis 不可用时的已确认方案为暂时拒绝新登录并提示服务不可用，不静默绕过限制；已签发 JWT 仍按 MySQL 用户登录版本与实时用户状态验证。此故障处理方案已确认；密码校验型换绑请求同样拒绝，返回 503。

## 19. 数据库表设计（已确认）

数据库表结构见 [数据库设计 v1.1](docs/database-design.md)，对应 [建表 SQL](db/schema.sql)。登录限制已改为 Redis，不再建立 MySQL 登录限制表；已确认使用用户表 token_version，不再建立登录会话表；帖子使用 images JSON 数组，不再建立独立图片表，当前共 7 张 MySQL 表。表设计及以下六项取舍已确认；尚未创建数据库或容器，尚未执行 SQL。


已确认的补充规则：

1. 联系方式保存在帖子 `contact_methods` JSON 数组中，至少一种，每项值最多 200 字符；不建立独立联系方式表，不按联系方式搜索。
2. 微信绑定保持一对一；MVP 支持验证平台密码后换绑，成功后旧绑定失效，失败保留旧绑定，不提供单独解绑入口。
3. 同一用户对同一帖子内容版本只能提交一次举报，重复请求返回原记录；帖子修改后可举报新版本，不同人的举报分别保存。
4. 每次提交保留完整审核快照，包括文字、联系方式与有序图片 Object Key 数组；快照提交后不可修改，图片文件不重复上传、不覆盖旧对象。
5. 首页按首次审核通过时间倒序，同时间按帖子 ID 倒序；重审通过不刷新首次发布时间。
6. 联系方式值最多 200 字符，举报说明、审核/举报处理原因和管理员日志原因最多 500 字符；MySQL 采用 8.4 系列，具体补丁版本与容器参数在实施时确定。

补充验收：超出联系方式/原因长度上限时拒绝提交且不截断；同一用户重复举报同一版本不会新增记录；管理员处理历史举报能查看当时的快照；重审通过不会改变首次发布时间；微信换绑失败不影响原绑定，成功后旧微信身份不能再通过绑定登录该账号。

## 20. RESTful 接口设计（已确认）

接口合同见 [飞书接口文档 v1.0](https://qcndrjmpg05r.feishu.cn/wiki/OQxmwWTdJiAT7LklqmQc5sgxnLc)，本地副本为 [接口文档](docs/api-design.md)，逐个列出 37 个接口的基本信息、请求参数和响应数据。2026-10-04 已确认原稿全部待审核项；文档定稿不代表后端或三端联调已完成。

1. 成功 code=1，失败为稳定字符串编码并使用对应 HTTP 状态；分页默认 20、最大 50，首次创建 201，其他 JSON 成功 200。
2. 网页使用同源代理、Origin/Referer 校验及 HMAC 双提交 CSRF，登录后绑定随机 JWT jti；不引入会话表。小程序使用 Bearer。
3. 微信换绑成功递增 token_version，使全部旧登录失效；首次绑定及绑定同一身份不递增。
4. 联系方式每项 1–200 字符；手机号为大陆 11 位数字，QQ 为 5–12 位数字，微信及其他允许非空文字。
5. 已完成帖子可编辑并重审，保留完成状态；已撤回不可编辑或恢复。标记/撤销完成仅允许审核通过且未撤回的帖子；撤回允许任意审核状态。
6. 用户不能举报自己的帖子；不同举报人分别保存同一版本的举报。
7. 管理员只能禁用或重置普通用户，不能通过 MVP 接口禁用或重置管理员。
8. 重置成功时只向本次授权管理员响应一次性返回随机临时密码，页面一次复制后线下交付，不保存或记录明文；不自动重试重置请求。
9. 登录及绑定相关请求按 IP 每分钟最多 30 次，账号规则仍为 5 次失败/10 分钟后暂停 10 分钟。Redis 不可用时拒绝新登录及密码校验型绑定，返回 503；现有 JWT 仍按 MySQL 验证。
10. 帖子创建用 Idempotency-Key 防重复；内容/状态及审核处理用 If-Match 防并发覆盖。每日额度仍使用 MySQL 事务。
