# 第一章 先搞懂：网页背后发生了什么

## 1.1 你每天都在用，只是没注意

场景：你在淘宝搜索框输入"耳机"，点搜索，屏幕上出现一列商品。

**这不到 1 秒的时间里，发生了三件事**：

```
① 浏览器把你的操作变成一条"请求"，通过网络发出去
        ↓
② 淘宝的服务器收到请求 → 去数据库里找所有耳机 → 打包成"响应"发回来
        ↓
③ 浏览器收到数据 → 画成你看到的商品列表
```

画成图：

```
┌──────────┐   ① 请求："给我所有耳机"     ┌────────────┐   ③ 查数据   ┌──────────┐
│  浏览器   │ ─────────────────────────▶ │   服务器    │ ──────────▶ │  数据库   │
│ (前端)    │                            │  (后端)     │ ◀────────── │  MySQL   │
│          │ ◀───────────────────────── │            │   ④ 返回结果 │          │
└──────────┘   ⑥ 画成界面   ⑤ 响应：数据  └────────────┘              └──────────┘
```

**关键认知**：浏览器只负责"画界面"和"发请求"，**真正干活的是服务器**。

> 我们写的"后端"，就是图里中间那个"服务器"。

## 1.2 服务器是什么？——一个"永远在等"的程序

对比一下两种程序：

**普通程序**（比如计算器）：运行 → 算出结果 → 结束退出。

**服务器程序**：启动后**不结束**，它挂在那里等：

```
启动 → 挂起等待 → 来了一个请求！→ 处理 → 返回结果 → 继续挂起等待 → ...
                 ↑                                      │
                 └──────────────────────────────────────┘
                            （永远循环，直到你手动关掉它）
```

这个"永远在等"的动作，在代码里就是最后这一行：

```go
// main.go 的最后一行
r.Run(":8080")
```

`Run` 会**一直阻塞在那里**，不会往下执行，也不会结束 —— 这就是为什么你双击 `lostfound.exe` 之后，
那个黑窗口一直开着不关。**它在等请求。**

`:8080` 是"端口号"，你可以理解成**门牌号**：
一台电脑上可以同时跑很多个服务，端口号用来区分"这个请求是找哪个服务的"。
我们占用了 8080 号门。

## 1.3 请求长什么样？——解剖一条 HTTP 请求

浏览器发给服务器的东西，原文长这样（这是真实的一条）：

```http
POST /api/items HTTP/1.1              ← 第 1 行：方法 + 路径
Host: localhost:8080                   ┐
Authorization: Bearer eyJhbGciOiJ...   │ 请求头（Header）
Content-Type: application/json         ┘   = 附加信息，像信封上写的备注
                                       ← 空行（必须有，用来分隔头和内容）
{"type":"lost","title":"校园卡"}        ← 请求体（Body）= 真正要传的数据
```

拆开看，一条请求只有 **4 个部分**：

| 部分 | 是什么 | 类比 |
|---|---|---|
| **方法** | 你要办什么事（见下表） | 去银行取号时选的业务类型 |
| **路径** | 你要找哪个功能 | 窗口号 |
| **请求头** | 附加信息（比如"我是谁"） | 信封上写的寄件人、备注 |
| **请求体** | 真正要传的数据 | 信封里的信纸 |

### 五个方法（记住这 5 个就够用）

| 方法 | 中文意思 | 我们项目里用来干嘛 |
|---|---|---|
| `GET` | **我要拿数据** | 查列表、查详情 |
| `POST` | **我要新建** | 注册、登录、发布帖子 |
| `PUT` | **我要整体修改** | 编辑帖子 |
| `PATCH` | **我要改一小部分** | 只改状态 |
| `DELETE` | **我要删除** | 删帖子 |

> 为什么要分这么细？因为"查"和"删"是完全不同的事，
> 分开之后，光看请求的第一行就知道对方想干嘛，不用看内容。

## 1.4 响应长什么样？——解剖一条 HTTP 响应

服务器回给浏览器的东西：

```http
HTTP/1.1 200 OK                        ← 第 1 行：状态码
Content-Type: application/json          ← 响应头
                                       ← 空行
{"code":0,"message":"ok","data":{...}}  ← 响应体：真正的数据
```

**状态码**是"这次请求的结果"，我们项目里只会出现这 5 个：

| 状态码 | 意思 | 什么时候出现 |
|---|---|---|
| `200` | 成功 | 一切正常 |
| `400` | 你传的参数有问题 | 比如密码只填了 3 位 |
| `401` | 你没登录（或登录过期了） | 没带 token 就想看联系方式 |
| `403` | 你登录了，但没权限 | 想改别人发的帖子 |
| `404` | 你要找的东西不存在 | 查一个不存在的帖子 ID |
| `500` | 服务器自己出错了 | 代码有 bug（我们要尽量避免） |

> **400 / 401 / 403 / 404 的区别很重要**，第六章还会细讲：
> 401 是"你是谁我不知道"，403 是"我知道你是谁，但你不能动这个"。

## 1.5 JSON 是什么？——双方约定好的"数据写法"

服务器和浏览器之间传数据，得用一种**双方都认识**的格式，我们用 JSON。

它长得像这样：

```json
{
  "code": 0,
  "message": "发布成功",
  "data": {
    "id": 4,
    "title": "校园卡",
    "status": "searching"
  }
}
```

**规则只有几条**：

| 规则 | 例子 |
|---|---|
| 用 `{}` 包一个"对象" | `{"name":"小明"}` |
| 键（key）**必须**用双引号 | `"name"` ✅ ｜ `name` ❌ |
| 值可以是字符串/数字/真假/null | `"小明"` / `18` / `true` / `null` |
| 用 `[]` 包一个"数组"（列表） | `[{"id":1},{"id":2}]` |
| 多项之间用逗号隔开 | `{"a":1,"b":2}` |

> **注意**：JSON 里**不能写注释**，也不能有多余的逗号（最后一项后面加逗号会报错）。
> 这是新手最常犯的两个错。

## 1.6 我们的项目：一句话说清

**"校园失物招领系统"就是一个存失物招领信息的服务**，规则是：

- **谁都能看** —— 列表、详情不用登录
- **登录了才能** —— 发帖、看联系方式、管理自己的帖子
- **自己的帖子才能** —— 改、删、改状态

对外提供 **12 个接口**（接口 = 一种"对话方式"）：

| 分类 | 接口 | 要登录吗 |
|---|---|---|
| 认证 | 注册、登录 | 不用 |
| 认证 | 获取当前用户、退出登录 | ✅ 要 |
| 物品 | 列表（搜索/筛选/分页）、详情 | 不用 |
| 物品 | 发布 | ✅ 要 |
| 物品 | 我的发布 | ✅ 要 |
| 物品 | 查看联系方式 | ✅ 要 |
| 物品 | 编辑、改状态、删除 | ✅ 要 + **必须是本人** |

# 第二章 我们用的三个工具

我们的项目没有"从零造轮子"，而是用了三个成熟的工具。先用大白话认识它们。

## 2.1 Gin —— 管"路由"的

**问题**：服务器收到请求后，怎么知道该交给哪段代码处理？

**答案**：查一张"对照表"，这张表就叫**路由表**。

```go
r.GET("/ping", func(c *gin.Context) {
    c.JSON(200, gin.H{"message": "pong"})
})
```

这一行意思是：**"有人用 GET 访问 `/ping` 时，执行后面这个函数"**。

但你可能有一堆疑问：`r` 是什么？`.GET` 是什么？后面那些参数是怎么定的？为什么能这么写？

**下面全部拆开讲。**

---

### 2.1.1 Gin 提供的三大类型

| 类型 | 是什么 | 怎么得到它 |
|---|---|---|
| `gin.Engine` | **引擎**：整个服务器的大脑 | `gin.Default()` |
| `gin.RouterGroup` | **路由分组**：一组路由的集合 | `引擎.Group("/api")` |
| `gin.Context` | **上下文**：一次请求的全部信息 | Gin 自动创建，作为参数传给你的处理函数 |

对应到我们的代码：

```go
r := gin.Default()            // r     是 *gin.Engine
api := r.Group("/api")        // api   是 *gin.RouterGroup
items := api.Group("/items")  // items 也是 *gin.RouterGroup（分组可以嵌套）

r.GET("/ping", func(c *gin.Context) {   // c 是 *gin.Context
    c.JSON(200, gin.H{"message": "pong"})
})
```

### 2.1.2 Gin 提供的两个"快捷类型"

| 类型 | 完整写法 | 用途 |
|---|---|---|
| `gin.H` | `map[string]any` | 快速拼 JSON 对象：`gin.H{"message": "pong"}` |
| `gin.HandlerFunc` | `func(*gin.Context)` | **处理函数的"标准形状"**（重点，见 2.1.4） |

### 2.1.3 Gin 提供的全部方法（我们项目用到的）

**A. 引擎/分组上的方法 —— 用来注册路由**

| 方法 | Gin 源码里的完整签名 | 用途 |
|---|---|---|
| `.GET(path, handlers...)` | `GET(relativePath string, handlers ...HandlerFunc) IRoutes` | 注册 GET 路由 |
| `.POST(path, handlers...)` | 同上 | 注册 POST 路由 |
| `.PUT(...)` / `.PATCH(...)` / `.DELETE(...)` | 同上 | 注册其他方法 |
| `.Group(path)` | `Group(relativePath string, handlers ...HandlerFunc) *RouterGroup` | 建子分组，**返回新分组对象** |
| `.Use(handlers...)` | `Use(middleware ...HandlerFunc) IRoutes` | 挂全局中间件 |
| `.Run(addr)` | `Run(addr ...string) error` | 启动服务、监听端口 |

**B. Context 上的方法 —— 在处理函数里用**

| 方法 | 用途 | 我们项目里用在哪 |
|---|---|---|
| `c.JSON(code, obj)` | 返回 JSON 响应 | `utils/response.go` |
| `c.ShouldBindJSON(&req)` | 解析请求体 + 按 `binding` 标签校验 | 所有 POST/PUT/PATCH 接口 |
| `c.Query("k")` | 取 URL 问号后的参数 | 列表的 keyword / type 等 |
| `c.DefaultQuery("k", "默认")` | 取 URL 参数，没有就用默认值 | 分页、状态筛选 |
| `c.Param("id")` | 取路径参数（`:id` 那段） | 详情、编辑、删除 |
| `c.GetHeader("k")` | 取请求头 | 中间件取 `Authorization` |
| `c.Set(k, v)` | 往上下文里**存**东西 | 中间件存 `user_id` |
| `c.GetUint(k)` | 从上下文里**取**（转成 uint） | controller 取 `user_id` |
| `c.Abort()` | **中断**：后面的处理函数不执行 | 中间件验不过时 |
| `c.Next()` | **放行**：交给下一个处理函数 | 中间件验过后 |

---

### 2.1.4 ★ 逐参数拆解：`items.GET("", controller.ListItems)`

先看 Gin 源码里 `GET` 方法的**完整签名**：

```go
func (group *RouterGroup) GET(relativePath string, handlers ...HandlerFunc) IRoutes
```

拆成三部分，逐个对应我们的代码：

| 签名里的部分 | 类型 | 我们传的 | 含义 |
|---|---|---|---|
| `group` | `*RouterGroup` | `items` | **接收者**：在哪个分组上注册（写在函数名**前面**） |
| `relativePath` | `string` | `""` | **相对路径**（相对于分组前缀） |
| `handlers` | `...HandlerFunc` | `controller.ListItems` | **处理函数**，可以传多个 |

#### ① `relativePath` 为什么是空字符串 `""`？

因为它是**相对路径**，不是完整路径。

```go
items := api.Group("/items")   // 分组前缀 = /api + /items = /api/items

items.GET("", ...)      // "" + 前缀    = /api/items
items.GET("/my", ...)   // "/my" + 前缀 = /api/items/my
items.GET("/:id", ...)  // "/:id" + 前缀 = /api/items/:id
```

> `""` 的意思是"**不加任何后缀，就用分组前缀本身**"。

#### ② `...HandlerFunc` 里的 `...` 是什么？

`...` 叫**变长参数**（variadic）：**这个位置可以传 0 个、1 个、或多个**。

```go
items.GET("", controller.ListItems)                           // 传 1 个
items.POST("", middleware.JWTAuth(), controller.CreateItem)   // 传 2 个
```

#### ③ `gin.HandlerFunc` 是什么？—— **这就是"参数怎么定"的答案**

它是一个**函数类型**，Gin 源码里的定义是：

```go
type HandlerFunc func(*gin.Context)
```

翻译成人话：**"接受一个 `*gin.Context` 参数、没有返回值的函数"**。

所以，**只要你的函数长成这个样子，就能传进去**：

```go
func ListItems(c *gin.Context) { ... }          // ✅ 符合：1 个参数，无返回值
func ListItems(c *gin.Context) error { ... }    // ❌ 不符合：多了返回值
func ListItems() { ... }                         // ❌ 不符合：没有参数
func ListItems(c *gin.Context, x int) { ... }   // ❌ 不符合：参数太多
```

打开 `controller/item_controller.go` 验证一下：

```go
func ListItems(c *gin.Context) {    // ← 和 HandlerFunc 的定义一模一样
    ...
}
```

> **所以"函数参数是怎么定的"这个问题的答案是**：
> **不是我们定的，是 Gin 在源码里规定好的，我们照着它的要求写函数。**
>
> 就像插座规定了插头的形状 —— 你的插头必须长成那个样子才能插进去。
> 用术语说，这叫"**实现了 `gin.HandlerFunc` 这个类型**"。

#### ④ 为什么中间件能和处理函数写在同一个调用里？

```go
items.POST("", middleware.JWTAuth(), controller.CreateItem)
//                 ↑ 第 1 个 handler      ↑ 第 2 个 handler
```

因为 `handlers` 是**变长参数**，传多个就**按顺序依次执行**：

```
请求进来
   ↓
执行 JWTAuth（第 1 个）
   ├─ 验过了 → 内部调用 c.Next() → 继续往下
   └─ 没验过 → 内部调用 c.Abort() → 到此为止，后面不执行
   ↓
执行 CreateItem（第 2 个）
```

**关键认知**：所谓"中间件"，**不是什么特殊的东西** ——
它就是一个**普通的处理函数**，只不过被放在列表的**前面**，
而且内部会调用 `c.Next()`（放行）或 `c.Abort()`（拦下）。

#### ⑤ 那一对大括号 `{ }` 是干嘛的？

```go
items := api.Group("/items")
{
    items.GET("", controller.ListItems)
    items.POST("", middleware.JWTAuth(), controller.CreateItem)
}
```

**纯粹为了好看，没有实际作用**，删掉照样能跑。

它是 Go 的**块语法**：把一组语句包起来，缩进之后**一眼看出"这些路由是同一组的"**。

### 2.1.5 小结：Gin 到底帮你做了什么

| 没有 Gin | 有 Gin |
|---|---|
| 自己解析 HTTP 请求原文 | 已经解析好了，`c` 里什么都有 |
| 自己写 if-else 匹配 URL | 注册一次，请求来了自动匹配 |
| 自己处理路径参数 `:id` | `c.Param("id")` 一行取出 |
| 自己把结构体转成 JSON | `c.JSON(200, obj)` 一行 |
| 自己实现"中间件"机制 | 写个普通函数，放进 handlers 列表就行 |

## 2.2 GORM —— 管"数据库"的

**问题**：数据存在 MySQL 里，Go 代码怎么跟它说话？

**笨办法**：手写 SQL 字符串。

```go
// 不用 GORM 的话，你得这么写（还得自己处理结果、防注入、拼参数……）
rows, _ := db.Query("INSERT INTO items (title, type) VALUES (?, ?)", title, type)
```

**用 GORM**：

```go
// dao/item_dao.go
func CreateItem(item *models.Item) error {
    return DB.Create(item).Error
}
```

一行搞定。GORM 会自动：

1. 看懂你传进来的 `item` 结构体
2. 生成对应的 SQL（`INSERT INTO items (...) VALUES (...)`）
3. 执行它
4. 把数据库生成的 ID 填回 `item.ID`

> **GORM 叫 ORM**（Object-Relational Mapping，对象关系映射）。
> 一句话：**让你用"操作 Go 对象"的方式操作数据库表**，不用手写 SQL。

## 2.3 JWT —— 管"身份"的

**问题**：HTTP 是"无记忆"的 —— 你登录了，但下一个请求过来，服务器怎么知道"你就是刚才登录的那个人"？

**答案**：登录成功后，服务器发给你一张"**通行证**"（就是 token），
之后你每次请求都带上它，服务器一看就知道你是谁。

这张通行证就是 **JWT**（JSON Web Token），长得像一串乱码：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjozLCJ1c2VybmFtZSI6ImRlbW8iLCJleHAiOjE3OTE4NjI0MzB9.JSq56Xlyq-eSLEuNzfZeFt1xYZwkeWV_MbVt3-uR9CE
```

它其实是用 `.` 分成三段的：

| 段 | 内容 | 能不能被看到 |
|---|---|---|
| 第 1 段 | 说明用什么算法签名 | 能（就是 Base64 编码，不是加密） |
| 第 2 段 | **真正的数据**：用户 ID、用户名、过期时间 | 能（同上） |
| 第 3 段 | **签名**：用密钥算出来的"防伪标记" | 不能伪造 |

**关键点**：前两段谁都能解开看（所以**别往 token 里放密码**），
但**第三段伪造不了** —— 因为算签名需要一个只有服务器知道的"密钥"。
服务器收到 token 时重新算一遍签名，对不上就说明这 token 是假的或被改过。

## 3.1 结构体 struct —— 把数据打包

**问题**：一个"用户"有用户名、密码、昵称……怎么把它们打包成一个整体？

**答案**：结构体。

```go
// models/user.go
type User struct {
    ID       uint
    Username string
    Password string
}
```

读法：`type User struct { ... }` = "定义一个新类型，叫 User，它包含这些字段"。

用起来：

```go
var u User            // 造一个空的 User
u.Username = "小明"    // 用点号访问字段
```

**重要规则：字段名首字母大写 = 公开，小写 = 私有。**

```go
type User struct {
    Username string   // 大写 → 别的包能访问 ✅
    password string   // 小写 → 只有 models 包自己能访问 ❌
}
```

> 为什么？Go 用大小写来控制"能不能被外部访问"（其他语言里通常写 `public` / `private` 关键字）。
> **我们的字段全部大写**，因为 controller、service、dao 都要访问它们。

## 3.2 struct tag —— 给字段贴标签

结构体字段后面反引号里的东西，叫 **tag（标签）**：

```go
// models/item.go
Title    string `gorm:"type:varchar(64);not null" json:"title"`
Contact  string `gorm:"type:varchar(100);not null" json:"-"`
```

**怎么理解**：就像给一个箱子贴了好几张标签，**不同的工具看不同的标签**：

| 标签 | 谁在看 | 作用 |
|---|---|---|
| `gorm:"..."` | GORM（数据库） | 建表时这一列叫什么类型、能不能为空 |
| `json:"..."` | 序列化（转成 JSON 时） | 这个字段输出成什么名字 |

**举个例子**：

```go
Username string `gorm:"type:varchar(32)" json:"username"`
```

- 数据库里：列名叫 `username`（GORM 默认把 `Username` 转成下划线小写），类型 `varchar(32)`
- 返回给前端：`"username": "小明"`

**如果 `json:"-"` 呢？**

```go
Password string `gorm:"type:varchar(100)" json:"-"`
```

`json:"-"` 的意思是：**转成 JSON 时，永远跳过这个字段**。

> 这是本项目最重要的一个技巧，第六章 6.2 会详细讲 ——
> 它让"密码"和"联系方式"**根本不可能**被泄露出去。

## 3.3 指针 `&` 和 `*` —— 房间号 vs 搬整个房间

这是新手最容易懵的概念，用比喻讲。

**场景**：你要把"一个用户的信息"交给别人。

**方式一：复制一份给他**（值传递）

```go
func showUser(u User) {   // 注意：没有星号
    // 这里拿到的是 User 的一份完整拷贝
    // 改动 u，不会影响原来的那个
}
```

好比：**把整个房间的东西搬一份到新房间**。安全，但如果房间很大，搬起来很费劲。

**方式二：告诉他房间号**（指针传递）

```go
func showUser(u *User) {  // 注意：有星号
    // 这里拿到的是"地址"，顺着地址能找到原来那个 User
    // 改动 u.Username，原来的也会变
}
```

好比：**只给他一个门牌号**。省事，而且他能直接进房间改东西。

**两个符号**：

| 符号 | 名字 | 意思 | 例子 |
|---|---|---|---|
| `*` | 解引用 / 声明指针类型 | "指向某个东西的地址" | `*User` = 指向 User 的指针 |
| `&` | 取地址 | "把这个东西的地址给我" | `&user` = user 的地址 |

**在我们的代码里**：

```go
// dao/item_dao.go
func GetItemByID(id uint) (*models.Item, error) {
    var item models.Item
    DB.First(&item, id)      // &item：把 item 的地址给 GORM，让它把查到的数据填进去
    return &item, nil        // 返回地址，而不是复制整个结构体
}
```

> **为什么查询要传 `&item`？**
> 因为 GORM 需要**往你的变量里写数据**。如果传的是拷贝，它写进拷贝里，
> 你原来的 `item` 还是空的 —— 这就是"要传地址"的原因。

## 3.4 方法 —— 给类型配一个专属函数

普通函数：

```go
func DSN(m MySQLConfig) string { ... }    // 调用：DSN(cfg.MySQL)
```

方法（多了一个"接收者"）：

```go
// config/config.go
func (m MySQLConfig) DSN() string { ... }  // 调用：cfg.MySQL.DSN()
```

区别就是函数名前面多了个 `(m MySQLConfig)`。

**怎么理解**：`(m MySQLConfig)` 里的 `m` 就是"这个对象自己"，
方法体里可以直接用 `m.Host`、`m.Port` 这些字段。

> 好比：`func 走路(人)` 是普通函数，`func (人) 走路()` 是方法 —— 走路是"人"这个类型自带的能力。
> 我们的项目里方法用得不多，主要是 `config.go` 里的 `DSN()`。

## 3.5 闭包 —— 能"记住"东西的函数

**普通函数**：给什么用什么，用完就忘。

**闭包**：函数里"记住"了外面的一些变量。

```go
// dao/item_dao.go（简化版）
build := func() *gorm.DB {
    tx := DB.Model(&models.Item{})
    if q.Keyword != "" {
        tx = tx.Where("title LIKE ?", "%"+q.Keyword+"%")   // ← 用到了外面的 q
    }
    return tx
}
```

这里的 `build` 就是一个闭包 —— 它记住了外面的 `q`（查询条件），
每次调用它，都能按 `q` 里的条件拼出查询。

**项目里两处用到闭包**：

| 位置 | 为什么用闭包 |
|---|---|
| `dao/item_dao.go` 的 `build` | 同样的查询条件要用两次（一次数总数、一次取数据），抽成闭包不用重复写 |
| `middleware/auth.go` 的 `JWTAuth()` | 它**返回一个函数**，而不是自己当处理函数（下一节细讲） |

## 3.6 接口 interface —— `any` 和 `error`

Go 里有两个你一定会反复见到的"接口"：

### `any`（= `interface{}`）

意思是"**任意类型**"。

```go
// utils/response.go
type Response struct {
    Code    int    `json:"code"`
    Message string `json:"message"`
    Data    any    `json:"data"`     // ← 这里能装任何东西
}
```

因为 `data` 有时候要装用户、有时候要装帖子、有时候要装列表，
所以声明成 `any`（什么都能装）。

### `error`

Go 处理错误的方式很特别：**错误就是一个普通的值**，用返回值往外传。

```go
func CreateItem(item *models.Item) error {
    return DB.Create(item).Error    // 成功返回 nil，失败返回错误
}
```

用的时候：

```go
err := dao.CreateItem(item)
if err != nil {          // nil 表示"没有错误"
    // 出错了，处理它
}
```

> 这就是为什么代码里到处都是 `if err != nil` —— 这不是啰嗦，
> 而是 Go 的设计哲学：**错误必须被显式处理，不能假装没看见**。

## 3.7 哨兵错误 —— 怎么区分"哪种错误"

`err != nil` 只能知道"出错了"，但出的是哪种错？

我们的做法：**预先定义几个"标准错误"**，然后比较。

```go
// service/errors.go
var (
    ErrUsernameTaken    = errors.New("用户名已被注册")
    ErrWrongCredentials = errors.New("用户名或密码错误")
    ErrItemNotFound     = errors.New("信息不存在")
    ErrNotOwner         = errors.New("只能操作自己发布的信息")
    ErrStatusBackward   = errors.New("状态只能前进，不能回退")
    ErrBadTime          = errors.New("时间格式不正确")
)
```

用的时候：

```go
// controller/item_controller.go
if errors.Is(err, service.ErrNotOwner) {
    utils.Fail(c, utils.CodeForbidden, err.Error())   // 翻译成 403
    return
}
```

> `errors.Is(错误A, 错误B)` = "A 是不是就是 B 这种错误？"
> 这些预定义好的错误值，行话叫"**哨兵错误**"（sentinel error）。

**为什么要这样？** 因为不同的错误要返回不同的 HTTP 状态码：

| 错误 | 翻译成 | 状态码 |
|---|---|---|
| `ErrItemNotFound` | "信息不存在" | 404 |
| `ErrNotOwner` | "只能操作自己发布的信息" | 403 |
| `ErrStatusBackward` | "状态只能前进，不能回退" | 400 |
| `ErrBadTime` | "时间格式不正确" | 400 |

# 第四章 一次请求的完整旅程（★ 最重要）

前面都是零件，这一章把它们装起来。

我们跟着一条真实的请求走一遍：**小明发布一条失物帖**。

## 4.0 前置：小明已经登录了

登录接口返回给他的 token：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjozLCJ1c2VybmFtZSI6ImRlbW8iLCJleHAiOjE3OTE4NjI0MzB9.JSq56Xlyq...
```

（前端会把它存在浏览器里，每次请求自动带上）

---

## 第 1 步：浏览器发出请求

> **🎯 这一步在干什么**
>
> **一句话**：前端把用户的操作（点了"发布"按钮）变成一条 HTTP 请求，通过网络发到服务器。
>
> **展开**：这条请求要告诉服务器四件事 ——
> ① **干什么**（`POST` = 新建）、② **找谁**（`/api/items`）、
> ③ **我是谁**（`Authorization` 里的 token）、④ **内容是什么**（下面那段 JSON）。
>
> 发出去之后，前端就**什么都不做，等着**，直到收到服务器的响应。

```http
POST /api/items HTTP/1.1
Host: localhost:8080
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
Content-Type: application/json

{
  "type": "lost",
  "title": "校园卡",
  "category": "card",
  "campus": "下沙校区",
  "place": "图书馆二楼",
  "happened_at": "2026-10-05 14:30",
  "description": "黑色卡套，里面有校园卡和饭卡",
  "contact": "微信 xiaoming123"
}
```

**读法**：
- `POST /api/items` → 我要**新建**一条，位置是 `/api/items`
- `Authorization: Bearer eyJ...` → **这是我的通行证**
- 空行下面的 JSON → 我要新建的内容

---

## 第 2 步：Gin 查路由表，找到处理函数

> **🎯 这一步在干什么**
>
> **一句话**：服务器收到请求，查表决定"这条请求该交给哪段代码处理"。
>
> **展开**：就像医院的分诊台 —— 你说"我要看牙"，分诊台告诉你"去 3 楼口腔科"。
> Gin 拿着 `POST /api/items` 去查路由表，查到两件事：
> ① 该执行 `controller.CreateItem`；
> ② 这条路由**挂了中间件**，所以得**先过中间件**才能到处理函数。
>
> **类比**：分诊台不但告诉你"去 3 楼"，还说"进 3 楼要先刷卡"。

请求到达服务器，Gin 引擎拿着 `POST /api/items` 去查路由表。

路由表是启动时登记好的（`router/router.go`）：

```go
// router/router.go（节选）
api := r.Group("/api")          // ❶ 建一个"分组"，前缀是 /api
items := api.Group("/items")    // ❷ 再建一个分组，前缀是 /api/items
{
    items.GET("", controller.ListItems)                        // → GET  /api/items
    items.POST("", middleware.JWTAuth(), controller.CreateItem) // → POST /api/items  ★ 命中！
    items.GET("/my", middleware.JWTAuth(), controller.MyItems)  // → GET  /api/items/my
    items.GET("/:id", controller.GetItem)                       // → GET  /api/items/123
    // ... 其他
}
```

**逐行解释**：

**❶ `api := r.Group("/api")`**

`Group` 是"分组" —— 用来给一组接口加**共同前缀**。
有了它，后面写 `items.GET("")` 就等于 `GET /api/items`，不用每次都写全。

**❷ `items := api.Group("/items")`**

再套一层分组，所以前缀变成 `/api` + `/items` = `/api/items`。

**❸ `items.POST("", middleware.JWTAuth(), controller.CreateItem)`**

这行是**关键**，它有三个部分：

| 位置 | 内容 | 含义 |
|---|---|---|
| 第 1 个参数 | `""` | 路径（空字符串 = 就用分组前缀本身） |
| 第 2 个参数 | `middleware.JWTAuth()` | **中间件**：进处理函数之前的"关卡" |
| 第 3 个参数 | `controller.CreateItem` | 真正的处理函数 |

> 📖 **这些参数的类型和规则是谁定的？** 见 **[2.1.4 逐参数拆解](#214--逐参数拆解itemsget-controllerlistitems)** ——
> 一句话：Gin 源码规定了 `GET(path string, handlers ...HandlerFunc)`，
> 我们照着它的要求写函数而已。

> **中间件为什么写在路由这一行？**
> 因为它要挂在**特定的接口**上。
> 你看 `items.GET("", controller.ListItems)` 这行就**没有**中间件 —— 因为列表是公开接口，谁都能看。
>
> **有中间件 = 要登录；没有 = 不用登录。** 一眼就能看出来。

**Gin 匹配结果**：`POST /api/items` → 命中第 2 行 → 先过 `JWTAuth` 中间件，再到 `CreateItem`。

> 顺带一提：`:id` 是**路径参数**，能匹配任意值。
> `GET /api/items/123` 会命中 `items.GET("/:id", ...)`，代码里用 `c.Param("id")` 取出 `"123"`。

---

## 第 3 步：中间件验明正身

> **🎯 这一步在干什么**
>
> **一句话**：检查你有没有带"通行证"、通行证是不是真的。验过了就放行，验不过就当场拦下。
>
> **展开**：从请求头里取出 token → 验签名（防伪造）+ 验有效期（防过期）→
> 验证通过后，把"你是谁"（user_id）**记到本次请求的记事本上** → 放行。
>
> **任何一步失败，就返回 401 并当场拦下 —— 后面的代码一行都不执行。**
>
> **类比**：进小区大门刷门禁卡。卡是真的、没过期 → 放行，保安顺便记下"3 号楼的小明来了"；
> 卡是假的或过期了 → 拦在门外，你根本进不了楼。

进入 `middleware/auth.go`：

```go
func JWTAuth() gin.HandlerFunc {
    return func(c *gin.Context) {
        // ① 从请求头里取 Authorization
        authHeader := c.GetHeader("Authorization")
        if authHeader == "" {
            utils.Fail(c, utils.CodeUnauthorized, "请先登录")
            c.Abort()
            return
        }

        // ② 按空格切成两段，校验格式
        parts := strings.SplitN(authHeader, " ", 2)
        if len(parts) != 2 || parts[0] != "Bearer" {
            utils.Fail(c, utils.CodeUnauthorized, "token 格式错误，应为：Bearer xxx")
            c.Abort()
            return
        }

        // ③ 解析 token
        claims, err := utils.ParseToken(parts[1])
        if err != nil {
            utils.Fail(c, utils.CodeUnauthorized, "登录已过期，请重新登录")
            c.Abort()
            return
        }

        // ④ 把用户信息存进 Context
        c.Set("user_id", claims.UserID)
        c.Set("username", claims.Username)

        c.Next()
    }
}
```

### 逐行拆解

**`func JWTAuth() gin.HandlerFunc {`**

注意：它**不是**直接的处理函数，而是**返回**一个处理函数。

为什么要这样绕一层？因为这样**将来能带参数**（比如 `JWTAuth("admin")` 表示"只允许管理员"）。
这是 Gin 社区的标准写法，照抄就行。

**`authHeader := c.GetHeader("Authorization")`**

`:=` 是 Go 的"声明并赋值"（短变量声明），等于"新建一个变量，类型自动推断"。
这里取请求头里 `Authorization` 那一行的值。

**`if authHeader == ""`**

如果取不到（客户端没带），说明没登录 → 返回 401。

**`parts := strings.SplitN(authHeader, " ", 2)`**

把 `"Bearer eyJhbGci..."` 按空格切一刀，最多切成 2 段：

```
parts[0] = "Bearer"
parts[1] = "eyJhbGciOiJIUzI1NiIs..."
```

**`if len(parts) != 2 || parts[0] != "Bearer"`**

校验格式：必须切成 2 段，而且第一段必须是 `Bearer`（这是 HTTP 的约定写法）。

**`claims, err := utils.ParseToken(parts[1])`**

拿着 token 去 `utils/jwt.go` 里验证：

```go
// utils/jwt.go
func ParseToken(tokenString string) (*CustomClaims, error) {
    token, err := jwt.ParseWithClaims(tokenString, &CustomClaims{}, func(t *jwt.Token) (any, error) {
        // 安全校验：确认对方用的就是 HS256
        if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
            return nil, fmt.Errorf("非预期的签名算法: %v", t.Header["alg"])
        }
        return jwtSecret, nil
    })
    if err != nil {
        return nil, err
    }

    claims, ok := token.Claims.(*CustomClaims)
    if !ok || !token.Valid {
        return nil, ErrTokenInvalid
    }
    return claims, nil
}
```

这个函数做三件事：
1. **验签名** —— 用密钥重新算一遍，对不上说明 token 被伪造/篡改过
2. **验过期** —— 检查 `exp` 字段（我们设的是 7 天）
3. **取出数据** —— 把 token 里装的 `user_id`、`username` 拿出来

`CustomClaims` 就是我们自己定义的"token 里装什么"：

```go
type CustomClaims struct {
    UserID   uint   `json:"user_id"`
    Username string `json:"username"`
    jwt.RegisteredClaims      // 内嵌：自动带上 exp（过期时间）、iat（签发时间）
}
```

**`c.Set("user_id", claims.UserID)`**

**关键一步**：把用户 ID 存进 `c`（这次请求的 Context，可以理解成"随身口袋"）。

为什么？因为中间件和后面的处理函数是**两个不同的函数**，没法直接传变量。
Context 就是它们之间的"传递通道"：中间件放进去，controller 拿出来。

**`c.Next()`**

放行，交给下一个处理函数（也就是 `controller.CreateItem`）。

### 如果验不过会怎样？

三个 `if` 里任意一个不通过，都会：

```go
utils.Fail(c, utils.CodeUnauthorized, "...")   // 返回 401
c.Abort()                                       // ★ 终止，后面的代码一行都不执行
return                                          // 从当前函数返回
```

**`c.Abort()` 是最容易漏的一行**！如果不写它，虽然返回了 401，
但**处理函数还会继续执行** —— 就会出现"未登录却把帖子删了"这种事故。

## 第 4 步：controller 收参数

> **🎯 这一步在干什么**
>
> **一句话**：把请求里的 JSON **文本**翻译成 Go 的**结构体**，并检查格式对不对。
>
> **展开**：JSON 是纯文本，Go 代码要用的是结构体，中间得有个"翻译"过程。
> `ShouldBindJSON` 一边翻译（按 `json` 标签逐字段填进去），一边检查（按 `binding` 标签验必填、长度、取值范围）。
>
> **有一样不合格就返回 400，不往下走。** 这样后面的 service 层可以放心假设"数据是干净的"。
>
> **类比**：餐厅服务员接单时先检查菜单填得对不对 —— 没写菜名、桌号填错，当场退回重填，
> 不会拿着糊涂单子跑进厨房。

中间件放行后，进入 `controller/item_controller.go` 的 `CreateItem`：

```go
func CreateItem(c *gin.Context) {
    // ① 解析请求体
    var req models.CreateItemRequest
    if err := c.ShouldBindJSON(&req); err != nil {
        utils.Fail(c, utils.CodeInvalidParam, "参数错误："+err.Error())
        return
    }

    // ② 取出中间件放的用户 ID
    userID := c.GetUint("user_id")

    // ③ 交给 service
    item, err := service.CreateItem(userID, req)
    if err != nil {
        handleItemError(c, err)
        return
    }

    // ④ 返回成功
    utils.OKMsg(c, "发布成功", item)
}
```

### 逐行拆解

**`var req models.CreateItemRequest`**

声明一个变量，类型是 `models.CreateItemRequest`（我们在 `models/item.go` 里定义的"发布请求长什么样"）。

```go
// models/item.go
type CreateItemRequest struct {
    Type        ItemType `json:"type" binding:"required,oneof=lost found"`
    Title       string   `json:"title" binding:"required,max=64"`
    Category    string   `json:"category" binding:"required,oneof=card electronics books clothing daily other"`
    Campus      string   `json:"campus" binding:"max=32"`
    Place       string   `json:"place" binding:"max=64"`
    HappenedAt  string   `json:"happened_at" binding:"required"`
    Description string   `json:"description" binding:"max=500"`
    Contact     string   `json:"contact" binding:"required,max=100"`
}
```

注意这里出现了第三种 tag：**`binding:"..."`** —— 这是给 **Gin 的参数校验器**看的：

| 规则 | 含义 |
|---|---|
| `required` | 必填，不传就报错 |
| `min=3,max=20` | 长度必须在 3~20 之间 |
| `oneof=lost found` | 只能是这两个值之一 |
| `omitempty` | 空的话就跳过校验（用在"选填"字段上） |

**`c.ShouldBindJSON(&req)`**

这一行干了两件事：

1. **解析**：把请求体里的 JSON 文本，按 `json:"xxx"` 标签**填进 `req` 结构体的对应字段**
   - `"title":"校园卡"` → `req.Title = "校园卡"`
2. **校验**：按 `binding:"..."` 标签检查每个字段

> **为什么要传 `&req`（取地址）？**
> 因为要把数据**写进** `req` 里。传拷贝的话，写进去你也拿不到（回忆 3.3 节）。

**`if err := c.ShouldBindJSON(&req); err != nil`**

如果校验不过（比如 `title` 没传），`err` 就不是 nil，返回 400：

```json
{"code":1001,"message":"参数错误：Key: 'CreateItemRequest.Title' Error:Field validation for 'Title' failed on the 'required' tag","data":null}
```

**`userID := c.GetUint("user_id")`**

从 Context 里取出中间件存的用户 ID。

> **为什么是 `GetUint` 而不是 `Get`？**
> 因为 `Get` 返回的是 `any`（任意类型），得自己做类型转换。
> `GetUint` 是 Gin 提供的便捷方法，直接返回 `uint`，取不到就返回 0。

**`item, err := service.CreateItem(userID, req)`**

把活交给下一层。注意这里**传了两个东西**：
- `userID` —— 从 token 里解出来的（可信）
- `req` —— 从请求体里来的（**不可信**，用户想传什么就传什么）

**`utils.OKMsg(c, "发布成功", item)`**

返回成功响应（下一节细讲）。

### controller 的定位

**controller 只做三件事**：收参数 → 调 service → 发响应。

它**不写业务逻辑**（比如"新帖状态必须是寻找中"这种规则不写在这），
那是 service 的活。这样分工的好处第五章讲。

## 第 5 步：service 做业务

> **🎯 这一步在干什么**
>
> **一句话**：真正"动脑子"的地方 —— 按业务规则加工数据，并守住安全底线。
>
> **展开**：把时间字符串转成时间类型、组装成数据库模型。**最关键的是两行"后端强制"**：
> - `Status` 固定为"寻找中" —— 不给前端传的机会
> - `UserID` 固定为当前登录用户 —— **绝不相信前端传的"我是谁"**
>
> **这是整个后端的安全底线**：前端传过来的一切都可能是伪造的，
> 只有从 token 里解出来的身份才可信。
>
> **类比**：厨师做菜时会按店里的规矩来（这道菜必须现做、不能加辣），
> 而不是全听客人怎么说 —— 否则客人说"我不要钱"你也认吗？

进入 `service/item_service.go`：

```go
func CreateItem(userID uint, req models.CreateItemRequest) (*models.Item, error) {
    // ① 解析时间字符串
    happenedAt, err := utils.ParseTime(req.HappenedAt)

        return nil, ErrBadTime

    // ② 组装成数据库模型
    item := &models.Item{
        Type:        req.Type,

        Description: req.Description,
        Contact:     req.Contact,

        UserID:      userID,                    // ★ 后端强制
    }

    // ③ 存进数据库
    if err := dao.CreateItem(item); err != nil {
        return nil, err
    }
    return item, nil
}
```

### 逐行拆解

**① 解析时间**

```go
happenedAt, err := utils.ParseTime(req.HappenedAt)
```

前端传来的 `happened_at` 是**字符串** `"2026-10-05 14:30"`，
但数据库里要存**时间类型**，所以得转换。

为什么不用 `time.Time` 直接接收？因为前端传的时间格式五花八门
（`2026-10-05 14:30`、`2026-10-05T14:30`、`2026-10-05`……），
所以我们在 `utils/time.go` 里挨个格式试：

```go
// utils/time.go
var timeLayouts = []string{
    time.RFC3339,          // 2026-09-26T14:30:00+08:00
    "2006-01-02T15:04:05", // 2026-09-26T14:30:00
    "2006-01-02T15:04",    // 2026-09-26T14:30
    "2006-01-02 15:04:05", // 2026-09-26 14:30:00
    "2006-01-02 15:04",    // 2026-09-26 14:30
    "2006-01-02",          // 2026-09-26
}

func ParseTime(s string) (time.Time, error) {
    for _, layout := range timeLayouts {
        if t, err := time.ParseInLocation(layout, s, time.Local); err == nil {
            return t, nil        // 试成功了就返回
        }
    }
    return time.Time{}, fmt.Errorf("无法识别的时间格式: %s", s)
}
```

> **Go 的时间格式很反直觉**：不用 `yyyy-MM-dd`，而是用一个"参考时间"
> `2006-01-02 15:04:05` 当模板（记住这个数就行：2006年1月2日下午3点4分5秒）。

**② 组装 `models.Item`（★ 重点看两行）**

```go
Status: models.StatusSearching,   // 新帖一律"寻找中"
UserID: userID,                    // 发布者 = 当前登录用户
```

**这两行是安全设计的核心**：

| 字段 | 前端能传吗 | 为什么 |
|---|---|---|
| `Status` | ❌ 不能 | 新帖必须从"寻找中"开始，不然有人一发布就是"已结束" |
| `UserID` | ❌ 不能 | 只能取 token 里解出来的 ID。如果让前端传，**任何人都能冒充别人发帖** |

> **记住这个原则**：**"你是谁"和"你的权限"永远从 token 里取，绝不相信前端传的值。**
> 前端传的一切都可能是伪造的。

`Category: models.ItemCategory(req.Category)` 这里做了一次类型转换：
`req.Category` 是普通 `string`，而 `Item.Category` 是 `ItemCategory` 类型
（`type ItemCategory string`，见 3.2 节的自定义类型），所以要转一下。

**③ 存数据库**

```go
if err := dao.CreateItem(item); err != nil {
    return nil, err      // 出错就往上传，让 controller 处理
}
return item, nil         // 成功：返回 item 和 nil（nil = 没有错误）
```

> 注意返回值的写法：`(*models.Item, error)` —— **Go 的函数可以返回多个值**，
> 这里同时返回"结果"和"错误"。调用方要先看 `err` 是不是 nil。

## 第 6 步：dao 存进数据库

> **🎯 这一步在干什么**
>
> **一句话**：把 Go 结构体变成一条 SQL，写进 MySQL。
>
> **展开**：我们只写了一行 `DB.Create(item)`，GORM 在背后做了三件事：
> ① 看懂结构体 → 生成 `INSERT INTO items (...) VALUES (...)`
> ② 自动填 `created_at` / `updated_at`
> ③ 把 MySQL 生成的**自增 ID 回填**到 `item.ID`（所以返回的 JSON 里才有 `"id": 4`）
>
> **类比**：仓库管理员收货。你只说"把这箱货入库"，他会自己登记、贴编号、告诉你货架号。

进入 `dao/item_dao.go`：

```go
func CreateItem(item *models.Item) error {
    return DB.Create(item).Error
}
```

**就一行**。拆开看：

| 部分 | 含义 |
|---|---|
| `DB` | 全局数据库连接（启动时通过 `dao.InitDB(db)` 注入的） |
| `.Create(item)` | GORM 的方法：把 `item` 插入数据库 |
| `.Error` | GORM 把错误放在 `.Error` 字段里，取出来返回 |

**GORM 在背后生成的 SQL**（你可以在 MySQL 里看到类似的）：

```sql
INSERT INTO items
  (type, title, category, campus, place, happened_at,
   description, contact, image_url, status, user_id, created_at, updated_at)
VALUES
  ('lost', '校园卡', 'card', '下沙校区', '图书馆二楼', '2026-10-05 14:30:00',
   '黑色卡套...', '微信 xiaoming123', '', 'searching', 3, NOW(), NOW());
```

**两个自动发生的事**：

1. **`created_at` / `updated_at` 自动填** —— GORM 认得出这两个名字特殊的字段，插入时自动填当前时间
2. **自增 ID 回填** —— MySQL 生成的 `id=4`，GORM 会自动写回 `item.ID`，
   所以后面返回给前端的 JSON 里能看到 `"id": 4`

## 第 7 步：返回响应

> **🎯 这一步在干什么**
>
> **一句话**：把结果打包成 JSON，原路返回给前端。
>
> **展开**：按 `json` 标签把结构体转成 JSON，套上统一格式 `{code, message, data}`，
> 用 HTTP 200 发回去。**注意 `contact` 字段凭空消失了** —— 因为 `json:"-"`（下面细讲）。
>
> **数据流向**：dao → service → controller → 响应，**原路返回**。
> 每一层只管把结果往上传，不关心上面怎么用。

回到 controller，执行最后一行：

```go
utils.OKMsg(c, "发布成功", item)
```

看 `utils/response.go`：

```go
// Response 是所有接口统一的响应结构
type Response struct {
    Code    int    `json:"code"`
    Message string `json:"message"`
    Data    any    `json:"data"`
}

func OKMsg(c *gin.Context, message string, data any) {
    c.JSON(http.StatusOK, Response{Code: CodeSuccess, Message: message, Data: data})
}
```

**`c.JSON(状态码, 数据)`** 是 Gin 的方法：把 `data` 转成 JSON 字符串，作为响应体发回去。

**最终发出去的响应**：

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"code":0,"message":"发布成功","data":{"id":4,"type":"lost","title":"校园卡","category":"card","campus":"下沙校区","place":"图书馆二楼","happened_at":"2026-10-05T14:30:00+08:00","description":"黑色卡套，里面有校园卡和饭卡","image_url":"","status":"searching","user_id":3,"created_at":"2026-10-06T11:33:51.132+08:00","updated_at":"2026-10-06T11:33:51.132+08:00"}}
```

### ★ 注意：返回的 JSON 里没有 `contact`！

我们明明把 `contact` 存进数据库了，为什么返回里没有？

因为 `models.Item` 里给这个字段加了 `json:"-"`：

```go
Contact string `gorm:"type:varchar(100);not null" json:"-"`
```

**`json:"-"` 的作用**：转成 JSON 时**永远跳过**这个字段。

所以：

| 操作 | contact 会怎样 |
|---|---|
| 存进数据库 | ✅ 正常存（`gorm` 标签不受影响） |
| 返回给前端 | ❌ 永远不出现（`json:"-"` 挡住了） |

**这就是"未登录看不到联系方式"的实现方式** —— 不是"查出来再删掉"，
而是**从结构上就不可能输出**。任何返回 `Item` 的接口（列表、详情、发布、编辑）都自动不带它。

想拿到联系方式？只能走专门的接口 `GET /api/items/:id/contact`（它挂了登录中间件）。

> 这个设计有多重要？如果哪天你手滑在列表接口里把 contact 也返回了，
> 那就等于把全站用户的微信号/QQ 公开了 —— PRD 里的验收点直接失败。
> 用 `json:"-"` 就从根上杜绝了这种失误。

## 4.2 第二个例子：小红搜索"校园卡"

再看一个例子，这次是**查询**，能覆盖"搜索 + 筛选 + 分页"。

### 请求

```http
GET /api/items?keyword=%E6%A0%A1%E5%9B%AD%E5%8D%A1&page=1&page_size=10
```

> `%E6%A0%A1%E5%9B%AD%E5%8D%A1` 是"校园卡"的 **URL 编码**。
> URL 里不能直接放中文，浏览器会自动编码，你不用管。

### 第 1 步：路由匹配

> **🎯 这一步在干什么**
>
> **一句话**：Gin 查表，发现这条路由**没有挂中间件**，直接交给处理函数。
>
> **展开**：为什么没有中间件？因为"看列表"是公开功能，**不登录也该能看**。
> 对比第 4 章的发布接口（挂了中间件），区别就在路由注册的那一行 ——
> **有中间件 = 要登录，没有 = 不用登录**，一眼能看出来。

```go
items.GET("", controller.ListItems)
```

**注意这里没有中间件** —— 因为列表是公开接口，不登录也能看。

### 第 2 步：controller 解析查询参数

> **🎯 这一步在干什么**
>
> **一句话**：从 URL 问号后面把筛选条件一个个取出来，凑成一个"查询条件对象"。
>
> **展开**：URL 里的 `?keyword=校园卡&page=1` 是"查询参数"（也叫 Query 参数），
> 用 `c.Query("keyword")` 取值、`c.DefaultQuery("page", "1")` 带默认值取值。
> 取完组装成 `ItemListQuery`，往下传给 service 和 dao。
>
> **和上一步的区别**：发布接口的参数在**请求体**（JSON）里，搜索的参数在 **URL** 里。
> 前者用 `ShouldBindJSON` 取，后者用 `Query` 取。

```go
func ListItems(c *gin.Context) {
    page, pageSize := parsePagination(c)

    // 状态默认只看"寻找中"
    status := c.DefaultQuery("status", string(models.StatusSearching))
    if status == "all" {
        status = ""
    }

    items, total, err := service.ListItems(models.ItemListQuery{
        Keyword:  c.Query("keyword"),
        Type:     c.Query("type"),
        Category: c.Query("category"),
        Campus:   c.Query("campus"),
        Place:    c.Query("place"),
        Status:   status,
        Page:     page,
        PageSize: pageSize,
    })
    // ...
}
```

**`c.Query("keyword")`** = 从 URL 的问号后面取值。

URL 长这样：`/api/items?keyword=校园卡&page=1`
`?` 后面是参数，`&` 分隔多个，`=` 连接名字和值。

**`c.DefaultQuery("status", "searching")`** = 带默认值的取值：
如果 URL 里没写 `status`，就用 `"searching"`。

> 这就是"首页默认只显示寻找中的信息"的实现 —— 前端不传，后端默认给"寻找中"。

**`parsePagination`** 是个辅助函数：

```go
func parsePagination(c *gin.Context) (int, int) {
    page, _ := strconv.Atoi(c.DefaultQuery("page", "1"))
    pageSize, _ := strconv.Atoi(c.DefaultQuery("page_size", "10"))
    if page < 1 {
        page = 1
    }
    if pageSize < 1 || pageSize > 50 {   // ★ 上限保护
        pageSize = 10
    }
    return page, pageSize
}
```

`strconv.Atoi` = "把字符串转成整数"（因为 URL 里取出来都是字符串）。
那个 `_` 是"我不关心这个返回值"（这里不关心转换错误，因为后面有兜底判断）。

**`pageSize > 50` 的保护很重要**：不设上限的话，
有人传 `page_size=999999` 就能一次把全库数据拉走，把服务器拖垮。

### 第 3 步：dao 拼 SQL（★ 本节重点）

> **🎯 这一步在干什么**
>
> **一句话**：按筛选条件拼出 SQL，**查两次** —— 一次数总数，一次取当页数据。
>
> **展开**：这一步有四个新手必踩的坑，下面逐个讲透：
> ① 为什么用闭包、为什么查两次
> ② `LIMIT` / `OFFSET` 怎么算分页
> ③ `LIKE` 怎么做模糊搜索、`?` 占位符为什么能防注入
> ④ 空结果为什么必须返回 `[]` 而不是 `null`

```go
func ListItems(q models.ItemListQuery) ([]models.Item, int64, error) {
    // ❶ 定义闭包：拼查询条件
    build := func() *gorm.DB {
        tx := DB.Model(&models.Item{})

        if q.Keyword != "" {
            like := "%" + q.Keyword + "%"
            tx = tx.Where("title LIKE ? OR description LIKE ?", like, like)
        }
        if q.Type != "" {
            tx = tx.Where("type = ?", q.Type)
        }
        if q.Status != "" {
            tx = tx.Where("status = ?", q.Status)
        }
        // ... 其他条件
        return tx
    }

    // ❷ 第一次调用：数总数
    var total int64
    if err := build().Count(&total).Error; err != nil {
        return nil, 0, err
    }

    // ❸ 第二次调用：取当页数据
    items := make([]models.Item, 0)
    err := build().
        Order("created_at DESC").
        Limit(q.PageSize).
        Offset((q.Page - 1) * q.PageSize).
        Find(&items).Error
    if err != nil {
        return nil, 0, err
    }
    return items, total, nil
}
```

#### ❶ 为什么要有 `build` 这个闭包？

因为**同样的查询条件要用两次**：
- 第一次：`SELECT COUNT(*) FROM items WHERE ...` —— 数一共多少条
- 第二次：`SELECT * FROM items WHERE ... ORDER BY ... LIMIT ...` —— 取当页数据

抽成闭包就不用把一堆 `if` 写两遍。

#### ❷ 为什么要数两次？只查一次不行吗？

**这是分页最容易踩的坑**，一定要理解：

前端要显示"共 3 条，当前第 1 页"，它需要知道 **total（总数）**。
如果只查一次、先 `Limit(10)` 再 `Count`，会发生什么？

```sql
-- 错误做法
SELECT COUNT(*) FROM items WHERE ... LIMIT 10;
```

`COUNT(*)` 只返回**一个数字**（总共多少条），`LIMIT 10` 对它毫无意义。
所以 total 永远等于实际总数 —— 等等，那没错啊？

**问题在于顺序**：如果你写的是

```go
tx.Limit(10).Count(&total)     // 先 Limit 再 Count
tx.Limit(10).Find(&items)
```

某些写法下 `Count` 会被 `Limit` 影响，导致 total 变成"最多 10"。
**新手最经典的 bug 就是：不管有多少数据，total 永远等于 page_size。**

所以我们的写法是：**用闭包重新拼一次干净的查询**，两次互不干扰。

#### ❸ `make([]models.Item, 0)` 和 `var items []models.Item` 的区别

**这个细节能救你的命**：

```go
var items []models.Item        // 查不到数据时 → JSON 里是 "list": null
items := make([]models.Item, 0) // 查不到数据时 → JSON 里是 "list": []
```

`null` 和 `[]` 的区别：

| 前端代码 | 拿到 `[]` | 拿到 `null` |
|---|---|---|
| `data.list.map(...)` | ✅ 正常（空数组，什么都不渲染） | 💥 **报错崩溃** |

所以**一定要用 `make(..., 0)` 初始化**，保证空结果返回的是 `[]` 而不是 `null`。

#### ❹ `LIMIT` / `OFFSET` 是怎么分页的？

| 参数 | 含义 | 第 1 页（每页 10 条） | 第 2 页 |
|---|---|---|---|
| `LIMIT` | 取几条 | 10 | 10 |
| `OFFSET` | 跳过几条 | 0 | 10 |

`Offset((q.Page - 1) * q.PageSize)` 这个公式：

- 第 1 页：`(1-1) * 10 = 0` → 跳过 0 条，取 10 条
- 第 2 页：`(2-1) * 10 = 10` → 跳过 10 条，取 10 条
- 第 3 页：`(3-1) * 10 = 20` → 跳过 20 条，取 10 条

#### ❺ `LIKE` 是怎么模糊搜索的？

```go
like := "%" + q.Keyword + "%"
tx = tx.Where("title LIKE ? OR description LIKE ?", like, like)
```

`%` 是"通配符"，代表"任意字符"。搜"校园卡"时，条件是：

```sql
WHERE title LIKE '%校园卡%' OR description LIKE '%校园卡%'
```

意思是：**标题或描述里"包含"这三个字的都算命中**。

| 数据库里的 title | 是否命中 |
|---|---|
| `校园卡` | ✅ |
| `我的校园卡丢了` | ✅ |
| `捡到一张校园卡和饭卡` | ✅ |
| `钥匙串` | ❌ |

**`?` 是占位符**（不是直接把值拼进 SQL 字符串）——
这是**防 SQL 注入**的关键。如果写成字符串拼接，别人传个恶意字符串就能删你的库。

### 第 4 步：返回

> **🎯 这一步在干什么**
>
> **一句话**：把"当页数据 + 总条数"一起返回，前端靠总条数判断还有没有下一页。
>
> **展开**：前端拿到 `total: 3`、当前 `list` 只有 2 条，就知道**还有下一页**；
> 用户往下滑时再发一次请求，把 `page` 改成 2。
>
> **为什么要给 total**：不给的话前端只知道"这一页有几条"，
> 没法判断是不是到底了，也就做不出"上拉加载更多"。

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "list": [ { "id": 4, "title": "校园卡", ... }, { "id": 3, "title": "钥匙串", ... } ],
    "total": 3,
    "page": 1,
    "page_size": 2
  }
}
```

前端拿到 `total: 3` 和当前 `list` 的长度 2，就知道**还有下一页**，
用户往下滑时再请求 `page=2`。

# 第五章 五层架构，一层一层讲

## 5.1 先用餐厅打个比方

我们的后端结构，跟一家餐厅的分工一模一样：

```
顾客（浏览器）
   ↓ 进门
前台接待（router）      —— 看你要办什么业务，指到对应窗口
   ↓
门口保安（middleware）  —— 查证件：有些业务要会员才能办
   ↓
服务员（controller）    —— 接单、上菜；不负责做菜
   ↓
厨师（service）         —— 真正的手艺：火候、配方、规矩
   ↓
仓库管理员（dao）       —— 只管取食材、放食材
   ↓
仓库（MySQL）           —— 食材存这里
```

**为什么这么分工？** 因为如果服务员既接单又做菜又管仓库，
哪天要换仓库（换数据库），整个餐厅都得停业改造。

## 5.2 每层详细说明

### 5.2.1 router（路由层）—— `router/router.go`

**一句话职责**：把"URL + 方法"翻译成"该执行哪个函数"。

#### 🎯 核心逻辑：一棵"路由树"

Gin 内部把注册的路由**组织成一棵树**。我们注册这几条：

```go
items.GET("", controller.ListItems)                          // /api/items
items.GET("/my", middleware.JWTAuth(), controller.MyItems)    // /api/items/my
items.GET("/:id", controller.GetItem)                        // /api/items/任意值
```

Gin 把它们拆成一段一段，拼成这样一棵树：

```
/api
 └─ /items
     ├─ (空)  ──▶ ListItems        ← GET /api/items
     ├─ /my   ──▶ MyItems          ← GET /api/items/my
     └─ /:id  ──▶ GetItem          ← GET /api/items/123
```

请求进来时，Gin 拿 URL 从根往下走，**一段一段匹配**：

```
GET /api/items/123  →  /api ✓ → /items ✓ → 没有 "123" 这个静态分支
                                          → 匹配参数分支 :id ✓
                                          → 执行 GetItem
```

#### 🔑 一个关键规则：静态优先于参数

树里 `/my` 和 `/:id` 是**兄弟**。当请求是 `/api/items/my` 时：

```
先试静态分支 /my  →  命中！用 MyItems
（不会去试 :id，否则 "my" 会被当成一个 id）
```

这就是为什么 `/api/items/my` 和 `/api/items/:id` 能共存 ——
**Gin 先找静态的，找不到才用参数兜底**。

> 顺带一提：这也是为什么 `/api/items/abc` 会落到 `:id` 上，
> 所以 controller 里必须用 `strconv.ParseUint` 校验（见 `parseID` 函数），
> 不能把字符串直接塞给数据库。

#### 📖 分组（Group）到底做了什么

```go
api := r.Group("/api")        // 建一个分组，记下前缀 "/api"
items := api.Group("/items")  // 再建一个，前缀 = "/api" + "/items" = "/api/items"
items.GET("", controller.ListItems)
```

**分组只是"记账"** —— 它记着"我这个组的前缀是什么"。
注册路由时，把"组前缀 + 你写的路径"拼起来，再插进树里。

所以 `items.GET("")` 和 `r.GET("/api/items", ...)` 是**完全等价**的，
分组的唯一好处是**少写重复的前缀**，而且让代码一眼能看出层次。

#### ❓ 如果没有它会怎样

你得在 `main` 里写一大串：

```go
// 没有 Gin 的话，你得自己解析请求，然后：
if r.Method == "POST" && r.URL.Path == "/api/items" {
    createItem(w, r)
} else if r.Method == "GET" && r.URL.Path == "/api/items" {
    listItems(w, r)
} else if strings.HasPrefix(r.URL.Path, "/api/items/") {
    // 还得自己把 id 从 URL 里抠出来……
}
```

几十个接口就是几十个 `if-else`，而且**顺序还不能错**（`/my` 必须写在 `/:id` 前面），
改一个接口要小心翼翼。Gin 把这套逻辑变成了"注册一次，自动匹配"。

### 5.2.2 middleware（中间件层）—— `middleware/auth.go`

**一句话职责**：请求到达真正的处理函数**之前**，先过的一道（或多道）关卡。

#### 🎯 核心逻辑：处理函数是一条"流水线"

这是理解中间件的关键。Gin 里，一次请求实际上会**按顺序执行一串函数**：

```
请求进来
   │
   ├─▶ [Logger]      ← 全局中间件（gin.Default() 自带，打印访问日志）
   │
   ├─▶ [Recovery]    ← 全局中间件（自带，某个函数 panic 了不会让服务挂掉）
   │
   ├─▶ [CORS]        ← 全局中间件（我们 r.Use 挂的，处理跨域）
   │
   ├─▶ [JWTAuth]     ← 路由中间件（挂在 POST /api/items 这条路由上）
   │        │
   │        └─ 验过了？调 c.Next() → 往下走
   │           没验过？调 c.Abort() → 到此为止
   │
   └─▶ [CreateItem]  ← 真正的处理函数
   │
响应返回
```

**"中间件"和"处理函数"本质上是同一种东西** ——
都是 `func(*gin.Context)`，都排在一个数组里，Gin 挨个执行。

区别只在于：
- **中间件**：排在前面，内部会调用 `c.Next()`（放行）或 `c.Abort()`（拦下）
- **处理函数**：排在最后，负责写响应

#### 📖 代码走读：`c.Next()` 和 `c.Abort()` 的作用

Gin 内部用一个**下标**记录"执行到第几个函数了"：

```go
// Gin 内部简化逻辑（不用记，理解意思就行）
c.index = 0                        // 从第 0 个开始
for c.index < len(c.handlers) {
    c.handlers[c.index](c)         // 执行当前这个
    c.index++                      // 下一个
}

func (c *Context) Next()  { c.index++; ...继续执行剩下的... }
func (c *Context) Abort() { c.index = 9999 }   // 下标直接跳到最后 → 循环结束
```

所以：

| 调用 | 效果 |
|---|---|
| `c.Next()` | 下标 +1，**继续执行后面剩下的函数**（包括处理函数） |
| `c.Abort()` | 下标跳到末尾，**循环立刻结束**，后面的函数一个都不执行 |
| 什么都不调 | 当前函数执行完，循环**自动**执行下一个 |

> ⚠️ 注意第三行：**就算你不写 `c.Next()`，中间件执行完也会自动往下走**。
> 所以"拦下"必须**显式**调用 `c.Abort()`，否则拦不住。
>
> 这就是为什么我们的中间件里，每个 `if` 分支都是：
> `返回 401` → `c.Abort()` → `return`，**三件事缺一不可**。

#### 📖 两种挂载方式的区别

```go
// ① 全局：所有路由都要过（router/router.go）
r.Use(cors.New(...))

// ② 路由级：只有这一条要过（挂在 handlers 列表里）
items.POST("", middleware.JWTAuth(), controller.CreateItem)
```

| | 全局中间件 `r.Use` | 路由中间件（写在 handlers 里） |
|---|---|---|
| 作用范围 | **所有**接口 | **只有这一条**路由 |
| 用在哪 | 日志、崩溃恢复、跨域 | 登录校验（因为有的接口要登录、有的不要） |

> **为什么登录校验不能挂全局？**
> 因为列表、详情、注册、登录这些接口**不需要登录**。
> 挂全局的话，连"注册"都要先登录 —— 死锁了。

#### ❓ 如果没有它会怎样

每个需要登录的接口都要自己写一遍这段：

```go
func CreateItem(c *gin.Context) {
    // 每个接口开头都抄一遍这 15 行
    authHeader := c.GetHeader("Authorization")
    if authHeader == "" { /* 401 */ return }
    parts := strings.SplitN(authHeader, " ", 2)
    if len(parts) != 2 || parts[0] != "Bearer" { /* 401 */ return }
    claims, err := utils.ParseToken(parts[1])
    if err != nil { /* 401 */ return }
    userID := claims.UserID
    // ... 终于可以开始写真正的业务了
}
```

8 个需要登录的接口 = 抄 8 遍。哪天 token 格式要改，**8 个地方都得改，漏一个就是漏洞**。

### 5.2.3 controller（控制器层）—— `controller/*.go`

**一句话职责**：**翻译官** —— 把 HTTP 世界的东西翻译给业务层，再把业务层的结果翻译回 HTTP。

#### 🎯 核心逻辑：两个世界之间的桥

```
   HTTP 世界                         业务世界
（字符串、JSON、状态码）          （结构体、业务错误）

  请求体 JSON 文本  ──解析──▶  models.CreateItemRequest
  URL 里的 "123"    ──转换──▶  uint(123)
  请求头里的 token  ──取出──▶  userID uint
                                      │
                                      ▼
                              service.CreateItem(...)
                                      │
   HTTP 200 + JSON  ◀──打包──  返回的 *models.Item
   HTTP 403 + 错误  ◀──翻译──  ErrNotOwner
```

**为什么需要这层"翻译"？** 因为 service 层**不该懂 HTTP**。
它不知道什么是状态码、什么是 JSON、什么是请求头 —— 它只管业务规则。

好处：哪天你要加一个"定时任务，每天自动把过期帖子标记为已结束"，
它可以直接调用 `service.UpdateStatus(...)`，**完全不用管 HTTP**。

#### 📖 代码走读：每个接口都是同一个骨架

```go
func CreateItem(c *gin.Context) {
    // ① 收参数：JSON 文本 → 结构体（顺带校验格式）
    var req models.CreateItemRequest
    if err := c.ShouldBindJSON(&req); err != nil {
        utils.Fail(c, utils.CodeInvalidParam, "参数错误："+err.Error())
        return
    }

    // ② 取出中间件放好的"我是谁"
    userID := c.GetUint("user_id")

    // ③ 交给业务层（注意传了两个东西：可信的 userID + 不可信的 req）
    item, err := service.CreateItem(userID, req)
    if err != nil {
        handleItemError(c, err)      // ← 错误翻译，见下
        return
    }

    // ④ 发响应
    utils.OKMsg(c, "发布成功", item)
}
```

打开 `controller/item_controller.go`，**8 个接口全是这个骨架**：
收参数 → 调 service → 判错误 → 发响应。唯一变的是中间那行调的是哪个 service 函数。

#### 🔑 核心机制：错误翻译器 `handleItemError`

这是 controller 层最值得看的一段代码。**service 层返回的是"业务错误"，
但前端需要的是"HTTP 状态码"**，中间得有个人翻译：

```go
func handleItemError(c *gin.Context, err error) {
    switch {
    case errors.Is(err, service.ErrItemNotFound):
        utils.Fail(c, utils.CodeNotFound, err.Error())       // → 404
    case errors.Is(err, service.ErrNotOwner):
        utils.Fail(c, utils.CodeForbidden, err.Error())      // → 403
    case errors.Is(err, service.ErrStatusBackward):
        utils.Fail(c, utils.CodeStatusBackward, err.Error()) // → 400
    case errors.Is(err, service.ErrBadTime):
        utils.Fail(c, utils.CodeInvalidParam, err.Error())   // → 400
    default:
        utils.Fail(c, utils.CodeServerError, "服务器开小差了") // → 500
    }
}
```

**这张表就是"业务错误 → HTTP 状态码"的映射规则**：

| service 返回的错误 | controller 翻译成 | 前端看到 |
|---|---|---|
| `ErrItemNotFound` | 404 + "信息不存在" | 东西没了 |
| `ErrNotOwner` | 403 + "只能操作自己发布的信息" | 你没权限 |
| `ErrStatusBackward` | 400 + "状态只能前进，不能回退" | 你的操作不合法 |
| 其他未知错误 | 500 + "服务器开小差了" | 后端出 bug 了 |

> **为什么集中在一个函数里？**
> 8 个接口都要处理这些错误，如果每个接口里写一遍 `switch`，
> 加一种新错误就要改 8 个地方。抽成一个函数，**只改一处**。
>
> 另外注意 `default` 分支：**没预料到的错误一律返回 500 且不暴露细节**。
> 直接 `err.Error()` 返回给前端可能泄露内部信息（比如数据库表名），
> 这是安全上的惯例。

#### 📖 收参数的三种方式（对应三种参数位置）

| 参数在哪 | 用什么收 | 例子 |
|---|---|---|
| **请求体**（JSON） | `c.ShouldBindJSON(&req)` | 发布、编辑、改状态 |
| **URL 问号后**（查询参数） | `c.Query("k")` / `c.DefaultQuery("k", "默认")` | 列表的 keyword、page |
| **URL 路径里**（`:id`） | `c.Param("id")` | 详情、编辑、删除 |

```go
// 路径参数：URL 是 /api/items/123，c.Param("id") 拿到字符串 "123"
id, err := strconv.ParseUint(c.Param("id"), 10, 64)   // 字符串 → 数字
if err != nil || id == 0 {
    utils.Fail(c, utils.CodeInvalidParam, "id 不合法")   // 比如 /api/items/abc
    return
}
```

#### ❓ 如果没有它会怎样

service 层就得自己解析 JSON、自己取请求头、自己拼 HTTP 状态码。
结果是 **service 和 HTTP 绑死**，任何非 HTTP 的调用方（定时任务、命令行工具、单元测试）
都没法复用它。

### 5.2.4 service（业务层）—— `service/*.go`

**一句话职责**：**整个后端唯一"懂业务"的地方** —— 所有"该不该""能不能""怎么算"都在这里。

#### 🎯 核心逻辑：它管三件事

| 职责 | 具体在干嘛 | 代码在哪 |
|---|---|---|
| **① 校验与权限** | 这条数据存在吗？是你发的吗？能这么改吗？ | `UpdateStatus`、`DeleteItem`、`UpdateItem` |
| **② 加工数据** | 时间字符串转成时间、密码加密、组装结构体 | `CreateItem`、`Register` |
| **③ 编排流程** | 先查 A，再根据 A 查 B，最后组装返回 | `GetItemDetail`、`Login` |

#### 📖 核心逻辑一：权限判断的固定套路

**所有"只能操作自己的东西"的接口，都是同一个三段式**：

```go
func UpdateStatus(userID, itemID uint, newStatus models.ItemStatus) error {
    // 第一步：东西存在吗？
    item, err := dao.GetItemByID(itemID)
    if err != nil {
        if errors.Is(err, dao.ErrNotFound) {
            return ErrItemNotFound        // → 404
        }
        return err                        // 数据库真出错了 → 500
    }

    // 第二步：是你的吗？
    if item.UserID != userID {
        return ErrNotOwner                // → 403
    }

    // 第三步：才轮到真正的业务逻辑
    if statusOrder[newStatus] <= statusOrder[item.Status] {
        return ErrStatusBackward          // → 400
    }
    return dao.UpdateItemFields(itemID, map[string]any{"status": newStatus})
}
```

**为什么"先查存在、再查归属"这个顺序不能反？**

| 顺序 | 结果 |
|---|---|
| 先查归属（拿 `item.UserID` 比较） | 但东西不存在时 `item` 是 nil，**直接崩** |
| 先查存在 ✅ | 不存在就 404 返回了，后面安全 |

而且**404 和 403 必须分开**：
- 东西不存在 → 404（"你要找的不在"）
- 东西存在但不是你的 → 403（"东西在，但不归你管"）

这两个混在一起会让用户困惑，也是 RESTful 的基本要求。

#### 📖 核心逻辑二：状态机为什么用 map 而不是 if-else

需求：`寻找中 → 已找到 → 已结束`，**只能前进，不能回退**。

**笨办法**（写 if-else 枚举所有情况）：

```go
// 三个状态要写 6 种判断，加第四个状态就要写 12 种……
if item.Status == "searching" && newStatus == "resolved" { /* ok */ }
if item.Status == "searching" && newStatus == "closed"   { /* ok */ }
if item.Status == "resolved"  && newStatus == "closed"   { /* ok */ }
// 剩下的都是非法……还得一个个列出来
```

**我们的办法**（把状态映射成序号，只比大小）：

```go
var statusOrder = map[models.ItemStatus]int{
    models.StatusSearching: 0,   // 寻找中
    models.StatusResolved:  1,   // 已找到
    models.StatusClosed:    2,   // 已结束
}

// 一行判断所有情况
if statusOrder[newStatus] <= statusOrder[item.Status] {
    return ErrStatusBackward
}
```

**这一个 `<=` 同时挡住了三种非法操作**：

| 情况 | 序号比较 | 结果 |
|---|---|---|
| 寻找中 → 已找到 | `1 > 0` | ✅ 放行 |
| 寻找中 → 已结束（跳级） | `2 > 0` | ✅ 放行（跳级也算前进） |
| 已找到 → 寻找中（回退） | `0 <= 1` | ❌ 拦住 |
| 已找到 → 已找到（原地） | `1 <= 1` | ❌ 拦住 |
| 已结束 → 任何 | `x <= 2` | ❌ 拦住 |

> **加第四个状态**（比如"已过期"）时，只要往 map 里加一行 `StatusExpired: 3`，
> 判断逻辑**一个字都不用改**。这就是"把规则抽成数据"的威力。

#### 📖 核心逻辑三：安全底线 —— 身份只从 token 来

看 `CreateItem` 里最关键的两行：

```go
item := &models.Item{
    ...
    Status: models.StatusSearching,   // ← 不看前端传什么，一律"寻找中"
    UserID: userID,                   // ← 来自 token，不是来自 req
}
```

注意 `userID` 是从哪来的：**中间件解析 token 得到的**，不是从 `req` 里读的。

```go
// controller 里
userID := c.GetUint("user_id")      // ← 中间件塞进 Context 的，来自 token
item, err := service.CreateItem(userID, req)   // req 是前端传的（不可信）
```

> **记住这条铁律**：**前端传的一切都可能是伪造的。**
> 如果 `user_id` 让前端传，别人改一下 JSON 就能以你的名义发帖。
>
> 判断"你是谁"只能靠 **token 里的签名**（伪造不了），
> 判断"你能不能干这事"只能靠 **数据库里的归属关系**。

#### 📖 核心逻辑四：编排 —— 一个请求查两次数据库

`GetItemDetail` 演示了 service 的"编排"职责：

```go
func GetItemDetail(id uint) (*models.ItemDetailResponse, error) {
    // 第一次查：帖子本身
    item, err := dao.GetItemByID(id)
    if err != nil { ... }

    // 第二次查：发帖人（因为详情页要显示发布者昵称）
    publisher, err := dao.GetUserByID(item.UserID)
    if err != nil { ... }

    // 组装成一个响应对象
    return &models.ItemDetailResponse{
        Item:               *item,
        PublisherNickname:  publisher.Nickname,
        PublisherStudentID: publisher.StudentID,
    }, nil
}
```

**dao 只会"查一张表"，service 负责"把多张表的数据拼起来"** —— 这就是分层的意义。

> ⚠️ 但要注意：**只有详情接口这么干，列表接口不查**。
> 列表一次返回 10 条，如果每条都去查一次发帖人，就是 11 次数据库查询（叫 **N+1 问题**）。
> 列表页 PRD 里也没要求显示昵称，所以干脆不查。

#### ❓ 如果没有它会怎样

这些规则会散落到 8 个 controller 里：

- `CreateItem` 里写一遍"新帖状态必须是 searching"
- `UpdateStatus` 里写一遍状态机
- `DeleteItem` 里写一遍权限判断
- `UpdateItem` 里再写一遍权限判断（**重复了**）

哪天产品说"状态允许回退"，你得翻遍所有文件找哪里写了状态判断 —— 而且**大概率会漏**。

### 5.2.5 dao（数据访问层）—— `dao/*.go`

**一句话职责**：**只管跟数据库打交道** —— 增、删、改、查，别的一概不管。

#### 🎯 核心逻辑：GORM 怎么把 Go 代码变成 SQL

理解 dao 层，先得理解 GORM 的**方法链**是怎么工作的。

```go
DB.Where("username = ?", username).First(&user)
```

这一行拆开看，是**三个动作串起来**：

```
DB                                   ← 拿到数据库连接
  .Where("username = ?", username)   ← 记下条件："WHERE username = 'tongshixuan'"
  .First(&user)                      ← 拼完整 SQL、执行、把结果填进 user
```

**`.Where()` 只是"记账"** —— 它不执行任何 SQL，只是把条件记在一个"待办清单"上。
真正执行的是最后一个方法（`First` / `Find` / `Create` / `Updates` / `Delete`）。

GORM 最终生成的 SQL：

```sql
SELECT * FROM users WHERE username = 'tongshixuan' ORDER BY id LIMIT 1;
```

> **为什么 `First` 会自动加 `ORDER BY id LIMIT 1`？**
> 因为"取第一条"必须有确定的顺序，否则数据库返回哪条是不确定的。
> GORM 按主键排序，保证结果稳定。

#### 📖 核心逻辑一：`?` 占位符 —— 防 SQL 注入的生命线

```go
DB.Where("username = ?", username)
```

**`?` 是占位符**，它的作用是把"数据"和"SQL 语句"**彻底分开**：

```
① 先编译 SQL 结构：  SELECT * FROM users WHERE username = ?
② 再把数据填进去：   'tongshixuan'
```

数据库**永远不会把数据当成 SQL 代码来执行**。

**如果偷懒写成字符串拼接会怎样？**

```go
// ❌ 千万别这么写
DB.Where("username = '" + username + "'")
```

用户在输入框里填这么一段：

```
' OR '1'='1
```

拼接后的 SQL 变成：

```sql
SELECT * FROM users WHERE username = '' OR '1'='1';
```

`'1'='1'` 永远成立 → **条件失效，全表数据都返回了**。
更狠的还能拼 `'; DROP TABLE users; --` 直接删表。

**记住**：所有要传进 SQL 的值，**一律用 `?` 占位**，绝不拼接。

#### 📖 核心逻辑二：错误翻译 `translate`

```go
// dao/dao.go
var ErrNotFound = errors.New("记录不存在")

func translate(err error) error {
    if errors.Is(err, gorm.ErrRecordNotFound) {
        return ErrNotFound          // GORM 的错误 → 我们自己的错误
    }
    return err                       // 其他错误原样返回
}
```

每个查询函数都套一层：

```go
func GetUserByID(id uint) (*models.User, error) {
    var user models.User
    if err := DB.First(&user, id).Error; err != nil {
        return nil, translate(err)   // ← 翻译一下再往上传
    }
    return &user, nil
}
```

**为什么多此一举？** 因为**上层不该认识 GORM**。

| | 不翻译 | 翻译 ✅ |
|---|---|---|
| service 层要写 | `errors.Is(err, gorm.ErrRecordNotFound)` | `errors.Is(err, dao.ErrNotFound)` |
| service 要 import | `gorm.io/gorm`（数据库库） | `lostfound/dao`（自己家的包） |
| 换数据库时 | 所有判断都得改 | **只改 `translate` 一个函数** |

这就是"**依赖倒置**"的实际体现：**上层依赖抽象（`dao.ErrNotFound`），不依赖具体实现（GORM）**。

#### 📖 核心逻辑三：分页为什么要查两次

`ListItems` 是 dao 里最复杂的一个，核心在这两行：

```go
var total int64
build().Count(&total)                          // 第一次：数一共多少条

items := make([]models.Item, 0)
build().Order("created_at DESC").Limit(...).Offset(...).Find(&items)  // 第二次：取当页
```

**为什么不能只查一次？** 因为前端需要两个不同的信息：

| 信息 | 用途 | 对应 SQL |
|---|---|---|
| **总数 total** | 判断"还有没有下一页" | `SELECT COUNT(*) FROM items WHERE ...` |
| **当页数据 list** | 渲染这一屏卡片 | `SELECT * FROM items WHERE ... LIMIT 10 OFFSET 0` |

这是两条**完全不同的 SQL**，所以得执行两次。

**`build` 闭包的作用**：这两条 SQL 的 WHERE 条件**一模一样**，
抽成闭包就不用把一堆 `if` 写两遍（详见第四章 4.2 第 3 步）。

#### 📖 核心逻辑四：更新为什么用 map 而不是结构体

```go
func UpdateItemFields(id uint, fields map[string]any) error {
    return DB.Model(&models.Item{}).Where("id = ?", id).Updates(fields).Error
}
```

调用时长这样：

```go
dao.UpdateItemFields(itemID, map[string]any{"status": newStatus})
```

**为什么传 map 不传结构体？** 因为 GORM 的 `Updates` 传结构体时会
**忽略零值字段**（空字符串、0、false）：

```go
// ❌ 如果传结构体：想把 description 改成空字符串
dao.UpdateItemFields(id, models.Item{Description: ""})
// GORM 会想："空字符串是零值，说明用户没填，跳过"
// 结果：description 根本没被修改！
```

**传 map 就没这个问题** —— map 里写了什么就更新什么，空字符串也会老老实实写进去。

#### ❓ 如果没有它会怎样

SQL 语句会散落在 service 各处：

```go
// service/item_service.go 里到处是这样的代码
var item models.Item
if err := dao.DB.Where("id = ?", id).First(&item).Error; err != nil { ... }
```

后果：
- **换数据库 = 灾难**：所有 SQL 散落在几十个地方，得一个个找
- **改表结构 = 灾难**：加个字段，不知道哪些查询受影响
- **测试困难**：想单独测业务逻辑，却发现它跟数据库绑死了

### 5.2.6 models（模型层）—— `models/*.go`

**一句话职责**：**定义"数据长什么样"** —— 全项目的"数据字典"。

#### 🎯 核心逻辑：三种"数据形状"，各管一段路

这是 models 层最重要的认知：**同一条数据，在旅程的不同阶段穿不同的"衣服"**。

```
前端发来     ┌─────────────────┐
的 JSON  ──▶ │ CreateItemRequest│  ① 请求模型：描述"前端能传什么"
             └─────────────────┘     带 binding 校验规则
                      │
                      │ service 加工（补上 status、user_id）
                      ▼
             ┌─────────────────┐
             │      Item       │  ② 表模型：描述"数据库存什么"
             └─────────────────┘     带 gorm 标签（建表规则）
                      │             带 json 标签（输出规则）
                      │ controller 打包
                      ▼
             ┌─────────────────────┐
             │ ItemDetailResponse  │  ③ 响应模型：描述"返回什么"
             └─────────────────────┘     比 Item 多两个发布者字段
```

**为什么要分三种？** 因为它们的**字段和规则完全不同**：

| | 请求模型 | 表模型 | 响应模型 |
|---|---|---|---|
| `status` 字段 | **没有**（前端不许传） | 有 | 有 |
| `user_id` 字段 | **没有**（防止冒充） | 有 | 有 |
| `contact` 字段 | 有（要传进来存） | 有 | **没有**（`json:"-"` 挡住） |
| 发布者昵称 | 没有 | 没有 | **有**（详情页要显示） |

> 如果图省事，**用一个结构体从头用到尾**会怎样？
> - 前端就能传 `status` 和 `user_id` 了 → **可以冒充别人发帖**
> - 返回时 `contact` 会跟着出去 → **联系方式泄露**
>
> 所以"多定义几个结构体"不是啰嗦，**是安全设计**。

#### 📖 核心逻辑：三种 tag，三个工具在"读"它

```go
Title   string `gorm:"type:varchar(64);not null" json:"title" binding:"required,max=64"`
```

同一个字段后面挂了三张"标签"，**被三个不同的工具读取**：

| tag | 谁在读 | 什么时候读 | 作用 |
|---|---|---|---|
| `gorm:"..."` | **GORM** | 启动建表 / 每次读写数据库 | 这列叫什么类型、能不能为空、要不要索引 |
| `json:"..."` | **Go 的 JSON 库** | 序列化/反序列化时 | 输出成什么字段名；`"-"` 表示**永不输出** |
| `binding:"..."` | **Gin 的校验器** | 收到请求、`ShouldBindJSON` 时 | 必填？多长？取值范围？ |

**这就是"一份定义，三处生效"** —— 写一次，建表、输出、校验全都有了。

#### 📖 核心逻辑：枚举为什么用"自定义类型 + 常量"

```go
type ItemStatus string          // 造一个新类型（底层还是字符串）

const (
    StatusSearching ItemStatus = "searching"
    StatusResolved  ItemStatus = "resolved"
    StatusClosed    ItemStatus = "closed"
)
```

**对比直接用字符串**：

```go
// ❌ 用裸字符串：写错了要等运行时才发现
if item.Status == "serching" { ... }     // 拼错了！但这行代码能编译通过
                                          // 上线后这个判断永远不成立 → 线上 bug

// ✅ 用常量：写错了编译期就报错
if item.Status == models.StatusSerching { ... }
// 编译失败：undefined: models.StatusSerching
```

**好处**：
1. **拼错立刻发现**（编译期 vs 上线后）
2. **IDE 能自动补全**（打 `models.Status` 就弹出三个选项）
3. **改值时只改一处**（哪天要把 `"searching"` 改成 `"pending"`，只改常量定义）
4. **类型安全**：`ItemStatus` 和 `ItemType` 是两个不同的类型，
   把 `ItemType` 赋给 `ItemStatus` 会编译报错，防止张冠李戴

#### ❓ 如果没有它会怎样

- controller 猜"service 要什么参数"，service 猜"dao 返回什么" —— **全凭记忆和默契**
- 表结构散落在各处 SQL 里，想加个字段不知道要改哪些地方
- 前端传什么、后端返回什么，没有一份**权威定义**，前后端各写各的，联调时全是 bug

### 5.2.7 utils（工具层）—— `utils/*.go`

**一句话职责**：跟业务无关的**通用工具** —— 谁都能用，谁都不依赖。

#### 🎯 核心逻辑：什么代码该放进 utils？

判断标准只有一条：**"它跟我们的业务有关系吗？"**

| 代码 | 该放 utils 吗 | 为什么 |
|---|---|---|
| 把密码加密 | ✅ 该 | 任何项目都这么加密，跟"失物招领"无关 |
| 生成/解析 token | ✅ 该 | 任何项目都能用 |
| 把时间字符串转成时间 | ✅ 该 | 纯技术问题 |
| 统一响应格式 | ✅ 该 | 所有接口共用 |
| "新帖必须是寻找中" | ❌ 不该 | 这是**业务规则**，属于 service |
| "只能改自己的帖子" | ❌ 不该 | 同上 |

#### 📖 核心逻辑：`response.go` —— 所有接口的"统一出口"

```go
type Response struct {
    Code    int    `json:"code"`
    Message string `json:"message"`
    Data    any    `json:"data"`
}

func OKMsg(c *gin.Context, message string, data any) {
    c.JSON(http.StatusOK, Response{Code: CodeSuccess, Message: message, Data: data})
}

func Fail(c *gin.Context, code int, message string) {
    c.JSON(httpStatus(code), Response{Code: code, Message: message, Data: nil})
}
```

**它解决的核心问题**：让 12 个接口的返回**长得一模一样**。

前端只需要写一次解析逻辑：

```js
const data = await res.json();
if (data.code !== 0) {  // 所有接口都是这个判断
    alert(data.message);
    return;
}
// 用 data.data
```

> **如果每个接口各返回各的格式**（有的 `{ok:true}`、有的 `{err:"..."}`、
> 有的直接返回数组），前端就得给每个接口写一套解析代码，改一个字段要改一片。
>
> 统一格式是**前后端协作的润滑剂**。

**另一个细节：`httpStatus()` 把业务码映射成 HTTP 状态码**

```go
func httpStatus(code int) int {
    switch code {
    case CodeUnauthorized: return http.StatusUnauthorized   // 1002 → 401
    case CodeForbidden:    return http.StatusForbidden      // 1003 → 403
    case CodeNotFound:     return http.StatusNotFound       // 1004 → 404
    case CodeServerError:  return http.StatusInternalServerError // 1008 → 500
    default:               return http.StatusBadRequest     // 其他 → 400
    }
}
```

**为什么两套都要？**

| | 业务码 `code` | HTTP 状态码 |
|---|---|---|
| 精细度 | 细（1001~1008） | 粗（400/401/403/404/500） |
| 谁看 | **前端代码**（决定提示什么文案） | **通用工具**（浏览器、Apifox、监控系统、Nginx 日志） |
| 例子 | `1007 状态只能前进` | `400` |

Apifox 里一眼能看出哪些接口返回 401/403，服务器监控也能直接统计"错误率" ——
**只返回 HTTP 200 + 业务码**的话，这些通用工具全都瞎了。

#### 📖 另外三个文件

| 文件 | 核心函数 | 干嘛的 |
|---|---|---|
| `jwt.go` | `GenToken` / `ParseToken` | 生成和验证"通行证"（签名防伪造、exp 防过期） |
| `password.go` | `HashPassword` / `CheckPassword` | bcrypt 加密/校验（自带随机盐、故意算得慢） |
| `time.go` | `ParseTime` | 把前端五花八门的时间格式统一转成 `time.Time` |

`time.go` 的实现思路很典型 —— **挨个试**：

```go
var timeLayouts = []string{
    time.RFC3339, "2006-01-02T15:04:05", "2006-01-02T15:04",
    "2006-01-02 15:04:05", "2006-01-02 15:04", "2006-01-02",
}

func ParseTime(s string) (time.Time, error) {
    for _, layout := range timeLayouts {
        if t, err := time.ParseInLocation(layout, s, time.Local); err == nil {
            return t, nil        // 试成功就返回
        }
    }
    return time.Time{}, fmt.Errorf("无法识别的时间格式: %s", s)
}
```

**为什么不用 `time.Time` 直接接收？** 因为前端传来的时间格式**不可控**
（`datetime-local` 控件给的是 `2026-10-05T14:30`，有人手写会写 `2026-10-05 14:30`），
用字符串接收再挨个试，**兼容性最好**。

#### ❓ 如果没有它会怎样

同样的代码在每个文件里抄一遍：
- `utils.Fail(c, ...)` 这行会变成每个 controller 里手写 `c.JSON(状态码, gin.H{...})`
- 加密逻辑可能在注册里写一份、改密码里再写一份，**哪天要换算法就得改好几处**
- 时间解析在每个需要时间的接口里各写一遍

**改一处要改 N 处，就是没抽工具层的代价。**

# 第六章 四个关键设计（面试官大概率问）

## 6.1 密码是怎么存的？

**❌ 错误做法**：明文存。数据库泄露 = 所有用户密码泄露。

**✅ 我们的做法**：bcrypt 哈希。

```go
// utils/password.go
func HashPassword(plain string) (string, error) {
    bytes, err := bcrypt.GenerateFromPassword([]byte(plain), bcrypt.DefaultCost)
    return string(bytes), err
}

func CheckPassword(plain, hash string) bool {
    return bcrypt.CompareHashAndPassword([]byte(hash), []byte(plain)) == nil
}
```

注册时：`明文密码` → `HashPassword` → 存进库。
数据库里长这样（谁也看不出原密码是什么）：

```
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
```

登录时：`用户输入的明文` + `库里的哈希` → `CheckPassword` → 返回 true/false。

**为什么不用 MD5 / SHA256？**

| | MD5 / SHA256 | bcrypt |
|---|---|---|
| 速度 | **快**（显卡一秒能算几十亿次） | **慢**（故意设计得慢） |
| 盐 | 需要自己加 | **自带随机盐** |
| 抗暴力破解 | 弱 | 强 |

黑客拿到哈希后想"反推出原密码"，只能一个个猜。**算得越慢，他越难**。
bcrypt 故意把每次计算拖慢到约 0.1 秒 —— 对正常登录没影响，
但黑客想试一亿个密码就得好几年。

**"自带随机盐"是什么意思？** 同一个密码 `123456`，两个用户加密出来的结果**完全不同**：

```
用户A：$2a$10$N9qo8uLOickgx2ZMRZoMye...
用户B：$2a$10$Xk7pQ3mNvB1cD4fG6hJ8kL...
```

所以黑客也没法"查表"（提前算好常见密码的哈希，拿去比对）。

## 6.2 联系方式为什么"看不到"？

**需求**（PRD 4.5）：联系方式不在列表和详情里展示，**登录后**才能通过"查看联系方式"看到。

**我们的做法**：`json:"-"`（第四章已经讲过，这里再总结一遍）。

```go
// models/item.go
Contact string `gorm:"type:varchar(100);not null" json:"-"`
```

**三个层次的安全性**：

| 层次 | 做法 | 效果 |
|---|---|---|
| 存储 | `gorm` 标签正常 | 数据库里存着，没问题 |
| **输出** | **`json:"-"`** | **任何返回 Item 的接口都自动不带它** |
| 访问 | 独立接口 + 登录中间件 | 想拿？先登录 |

**面试官可能问**："我未登录，能不能改 URL 拿到别人的联系方式？"

**答**：
> 不能。列表和详情的响应结构里**根本没有这个字段** —— 不是"查出来再过滤掉"，
> 是序列化时就跳过了。唯一的出口是 `GET /api/items/:id/contact`，
> 而这个接口挂了 `JWTAuth` 中间件，没有有效 token 直接返回 401。

**如果面试官追问**："那我把 token 伪造一下呢？"

**答**：
> 伪造不了。token 的第三段是签名，用服务器才知道的密钥算出来的。
> 服务器每次收到 token 都会重新算一遍签名，对不上就拒绝（`utils/jwt.go` 里会验）。

## 6.3 状态为什么不能回退？

**需求**（PRD 4.4）：`寻找中 → 已找到 → 已结束`，**只能前进不能回退**。

**实现**（`service/item_service.go`）：

```go
var statusOrder = map[models.ItemStatus]int{
    models.StatusSearching: 0,
    models.StatusResolved:  1,
    models.StatusClosed:    2,
}

func UpdateStatus(userID, itemID uint, newStatus models.ItemStatus) error {
    // ... 先查帖子、校验是不是本人 ...

    if statusOrder[newStatus] <= statusOrder[item.Status] {
        return ErrStatusBackward    // 序号没变大 → 拒绝
    }
    return dao.UpdateItemFields(itemID, map[string]any{"status": newStatus})
}
```

**为什么用"序号比较"而不是写一堆 if-else？**

如果写 if-else，规则是：`寻找中→已找到` ✅、`已找到→已结束` ✅、
`寻找中→已结束` ✅（跳过一级也算前进）、`已找到→寻找中` ❌……

三个状态就要写 6 种情况的判断。**用序号只写一行**：

```
新状态序号 > 当前状态序号  →  允许
```

将来加第四个状态，只要往 map 里加一行，判断逻辑不用改。

**配套的坑（很重要）**：编辑接口 `PUT /api/items/:id` **故意不给改 status**。

```go
// models/item.go
type UpdateItemRequest struct {
    Title       string `json:"title" ...`
    // ... 注意：没有 Status 字段！
}
```

如果编辑接口能改 status，用户 `PUT` 一下就能把"已结束"改回"寻找中"，
状态机就形同虚设了。

## 6.4 退出登录为什么"什么都没做"？

看 `controller/user_controller.go` 的 `Logout`：

```go
func Logout(c *gin.Context) {
    utils.OKMsg(c, "已退出登录（前端请删除本地保存的 token）", nil)
}
```

**它真的什么都没做** —— 但这是**正确**的，不是偷懒。

**原因**：JWT 是**无状态**的。

| | 传统 Session | JWT（我们用的） |
|---|---|---|
| 服务端存记录吗 | ✅ 存（记着"谁登录了"） | ❌ 不存 |
| 退出登录怎么做 | 删掉服务端的记录 | **服务端没法删（没记录可删）** |
| 能强制下线吗 | ✅ 能 | ❌ 不能（除非额外上 Redis 黑名单） |

**打个比方**：
- Session 像**酒店房卡**：退房时前台把卡注销，卡就失效了
- JWT 像**演唱会门票**：票在你手上，主办方**没法让已经卖出去的票作废**

所以"退出登录"真正发生的地方是**前端**：把本地存的 token 删掉，
之后的请求就不带它了（也就相当于"未登录"了）。

**保留这个接口的意义**：
1. 满足任务书"退出登录"的要求
2. 前端有一个统一的收尾调用点
3. 将来如果改成 Redis 黑名单方案，前端代码不用动

**面试官可能问**："那用户 token 被盗了怎么办？"

**答**：
> 这正是 JWT 的取舍。要解决得引入 Redis 黑名单：把要作废的 token 存起来，
> 每次请求查一下。但那样就失去了 JWT"无状态、不用查库"的优势。
> 我们项目规模小，选择了简单方案；token 有效期设的是 7 天。

# 第七章 前端是怎么工作的

前面六章都在讲后端。这一章补上另一半：**用户直接看到的那部分（前端）是怎么动起来的**。

## 7.1 前端三件套：各管什么

前端就是三个东西，各管一摊：

| 文件类型 | 管什么 | 类比 |
|---|---|---|
| **HTML**（`.html`） | **结构**：页面上有哪些东西 | 房子的**骨架**（哪里是墙、哪里是门） |
| **CSS**（`.css`） | **样式**：这些东西长什么样 | 房子的**装修**（颜色、大小、间距） |
| **JavaScript**（`.js`） | **行为**：用户操作时发生什么 | 房子的**水电**（按开关灯就亮） |

打开我们的 `web/index.html` 看：

```html
<!-- ① 结构：有哪些东西 -->
<div class="search-wrap">
  <div class="search-box">
    <span class="icon">🔍</span>
    <input id="keyword" type="search" placeholder="搜一搜：校园卡、耳机、钥匙…">
  </div>
</div>

<!-- ② 引入样式 -->
<link rel="stylesheet" href="css/style.css">

<!-- ③ 引入行为 -->
<script src="js/api.js"></script>
<script src="js/index.js"></script>
```

**HTML 里那些 `class="..."` 是干嘛的？**
它们本身不影响显示，只是**给 CSS 和 JS 打的"标记"** ——
CSS 靠它找到元素来上色，JS 靠它找到元素来绑定点击事件。

## 7.2 一个页面从打开到显示的完整过程

这是理解前端的**关键**，一定要搞懂：

```
① 你在浏览器输入 http://localhost:8080/app/
        ↓
② 服务器返回 index.html 的文本内容
        ↓
③ 浏览器开始解析这份 HTML，遇到 <link> 就去下载 CSS
   （下载期间它不会傻等，继续往下解析）
        ↓
④ 遇到 <script> 就去下载 JS 文件
        ↓
⑤ 浏览器按 HTML + CSS 把界面**画出来**
   ⚠️ 注意：此时列表区域是空的！因为数据还没拿到
        ↓
⑥ JS 开始执行：调用后端接口 /api/items 拿数据
        ↓
⑦ 拿到数据后，JS 把数据"拼"成 HTML 字符串，塞进页面
        ↓
⑧ 你看到完整的列表
```

**核心认知：页面是先画出来、数据后填进去的。**

```js
// web/js/index.js —— 第 ⑦ 步干的事
box.innerHTML = state.list.map(cardHtml).join('');
//              ↑ 把数组里的每条数据，用 cardHtml() 拼成 HTML，一起塞进页面
```

```js
// cardHtml 就是"数据 → HTML"的模板
function cardHtml(item) {
  return `
    <div class="card" data-id="${item.id}">
      <span class="tag ${item.type}">${TYPE_TEXT[item.type]}</span>
      <span class="card-title">${escapeHtml(item.title)}</span>
      <span class="badge ${item.status}">${statusText(item)}</span>
    </div>
  `;
}
```

> **为什么要这样设计？**
> 因为数据是**变的**（今天 3 条帖子，明天 30 条）。
> 如果 HTML 里写死内容，每来一条新数据都得改网页文件。
>
> 现在这样：**HTML 只写"空壳"，JS 负责把数据填进去** ——
> 这叫"**前后端分离**"，页面文件不用动，数据变了页面自动变。

## 7.3 前端怎么跟后端说话：`fetch`

浏览器内置了一个函数叫 `fetch`，专门用来发 HTTP 请求：

```js
// 最简形式：GET 请求
const res  = await fetch('http://localhost:8080/api/items');
const data = await res.json();     // 把响应的 JSON 文本解析成对象
```

拆开看：

| 部分 | 含义 |
|---|---|
| `fetch(地址)` | 发一条 HTTP 请求（默认是 GET） |
| `await` | "等结果回来再往下走"（网络请求要时间，不能立刻拿到） |
| `res` | 服务器的响应对象 |
| `res.json()` | 把响应体里的 JSON **文本**解析成 JS 对象 |

**发 POST 请求（带数据）**：

```js
const res = await fetch('http://localhost:8080/api/items', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ title: '校园卡', type: 'lost' }),   // 对象 → JSON 文本
});
```

> **`JSON.stringify()` 和 `res.json()` 是一对反操作**：
> - `JSON.stringify(对象)` → JSON **文本**（发给后端）
> - `res.json()` → 把文本变回**对象**（后端发来的）

我们在 `web/js/api.js` 里把 fetch **包了一层**，这样每个页面就不用重复写这些：

```js
async function request(method, path, body, opts = {}) {
  // ① 自动带上 token
  const headers = { 'Content-Type': 'application/json' };
  const token = getToken();
  if (token) headers['Authorization'] = 'Bearer ' + token;

  // ② 发请求
  const res = await fetch(API_BASE + path, { method, headers, body: ... });

  // ③ 自动解析 JSON
  const data = await res.json();

  // ④ 自动处理 401（登录过期）
  if (res.status === 401) {
    clearToken();
    toast('请先登录');
    setTimeout(() => location.href = 'login.html', 700);
    throw new Error(data.message);
  }

  // ⑤ 自动判断业务错误
  if (data.code !== 0) throw new Error(data.message);

  return data.data;     // ⑥ 只把有用的部分返回给页面
}
```

**包这一层的好处**：页面代码变成这样，干净得多：

```js
// 页面里只要写这一行，token、解析、错误处理全自动
const data = await api.get('/items?page=1');
```

## 7.4 token 存在哪？怎么自动带上？

**存哪**：浏览器的 `localStorage`（本地存储，关掉浏览器再打开还在）。

```js
localStorage.setItem('lostfound_token', token);   // 存
localStorage.getItem('lostfound_token');          // 取
localStorage.removeItem('lostfound_token');       // 删（退出登录）
```

**怎么自动带上**：在 `api.js` 的 `request()` 里，每次请求前自动加请求头：

```js
if (token) headers['Authorization'] = 'Bearer ' + token;
```

所以页面代码**完全不用管 token** —— 存一次，之后所有请求自动带。

**完整的生命周期**：

```
登录成功 → setToken() 存进 localStorage
    ↓
之后每个请求 → request() 自动读出来，放进 Authorization 头
    ↓
退出登录 → clearToken() 删掉，之后的请求就不带了
    ↓
token 过期 → 后端返回 401 → api.js 自动清掉 + 跳登录页
```

> **为什么不用 Cookie？** Cookie 每次请求自动带上，但**容易被 CSRF 攻击**
> （别的网站可以诱导你的浏览器发请求，自动带上你的 Cookie）。
> 用 `localStorage` + 手动加 Header 的方式，**别的网站读不到你的 localStorage**，
> 也就伪造不了这个请求头。

## 7.5 我们的 6 个页面分别干什么

| 页面 | 文件 | 核心逻辑 |
|---|---|---|
| **首页** | `index.html` + `index.js` | 收集筛选条件 → 请求 `/items` → 拼成卡片渲染；滚到底自动加载下一页 |
| **详情页** | `detail.html` + `detail.js` | 请求 `/items/:id`；判断"是不是我发的"决定显示什么按钮 |

| **我的** | `my.html` + `my.js` | 请求 `/auth/me` 拿个人信息 + `/items/my` 拿我的发布 |
| **登录** | `login.html` + `login.js` | 请求 `/auth/login` → 存 token → 跳回原页面 |
| **注册** | `register.html` + `register.js` | 请求 `/auth/register` → **顺手自动登录** → 进首页 |

**两个值得一提的细节**：

**① 详情页怎么知道"这条是我发的"？**

```js
// 同时问两个问题
item = await api.get('/items/' + itemId);        // 这条帖子是谁发的（item.user_id）
me   = await api.get('/auth/me');                // 我是谁（me.id）

isOwner = (item.user_id === me.id);              // 一比就知道
```

是本人 → 显示「标记为已找到」「编辑」「删除」
不是本人 → 显示「查看联系方式」

**② 发布页怎么同时当"新建"和"编辑"用？**

```js
const editId = getQuery('id');      // URL 里有没有 ?id=
const isEdit = !!editId;

// 提交时
if (isEdit)  await api.put('/items/' + editId, body);   // 编辑
else         await api.post('/items', body);            // 新建
```

**同一个页面文件，靠 URL 参数切换模式** —— 省得写两套几乎一样的代码。

# 第八章 接口：前后端之间的"合同"

第七章讲了前端怎么发请求，第四章讲了后端怎么处理请求。
这一章把它们**接起来**：**双方凭什么能对上？**

## 8.1 接口到底是什么

**一句话**：接口 = **前后端约定好的一种"对话方式"**。

打个比方 —— **点外卖**：

| 外卖 | 我们的接口 |
|---|---|
| 菜单上写着"宫保鸡丁，25 元，可选微辣/中辣/特辣" | 接口文档写着"发布接口，需要 title/type/category 等字段" |
| 你按菜单点：宫保鸡丁、中辣 | 前端按约定发：`{"title":"校园卡","type":"lost"}` |
| 商家按菜单做，端出来一盘菜 | 后端按约定处理，返回 `{"code":0,"data":{...}}` |

**关键**：**双方都得按同一份菜单来**。
你点"宫保鸡丁不要花生"，但菜单上根本没有"不要花生"这个选项 —— 商家只能忽略或报错。

## 8.2 一份接口"合同"包含哪些内容

看我们的发布接口，一份完整的"合同"有 **5 个要素**：

```http
POST /api/items                              ← ① 方法 + ② 路径
Authorization: Bearer eyJhbGciOiJIUzI1...    ← ③ 要带什么头
Content-Type: application/json
                                             ← 空行
{                                            ┐
  "type": "lost",                            │
  "title": "校园卡",                          ├ ④ 请求体：要传什么
  "category": "card",                        │
  "happened_at": "2026-10-05 14:30",         │
  "contact": "微信 xiaoming123"               │
}                                            ┘
```

⑤ **返回什么**：

```json
{
  "code": 0,
  "message": "发布成功",
  "data": { "id": 4, "title": "校园卡", "status": "searching", ... }
}
```

**五个要素缺一不可**：

| 要素 | 说清楚什么 | 不说清楚会怎样 |
|---|---|---|
| ① 方法 | 是"查"还是"新建" | 前端用 GET 发数据，后端收不到 |
| ② 路径 | 找哪个功能 | 404 |
| ③ 请求头 | 要不要登录、带什么格式 | 401 或解析失败 |
| ④ 请求体 | 要传哪些字段、什么类型、哪些必填 | 400 |
| ⑤ 响应 | 返回什么结构、错误怎么表示 | 前端不知道怎么取数据 |

**我们的这份"合同"写在哪？** 三个地方，内容必须一致：

| 位置 | 形式 | 给谁看 |
|---|---|---|
| `models/*.go` 里的结构体 | Go 代码 | **后端自己执行**（Gin 照着它解析校验） |
| `docs/API接口文档.md` | 人话文档 | **前端开发者**（照着它写请求） |
| `docs/openapi.json` | 机器可读 | **Apifox**（导入即得测试工具 + 在线文档） |

## 8.3 ★ 完整例子：点一下"查看联系方式"，背后发生了什么

这是把**前端 + 接口 + 后端**串起来的完整链路。跟着走一遍，你就全通了。

**场景**：小明在详情页看到一条别人发的失物帖，点了「查看联系方式」。

```
【前端侧】
① 用户点击按钮
   HTML:  <button id="btnContact">查看联系方式</button>
   JS:    document.getElementById('btnContact').onclick = showContact

② showContact() 开始执行，先检查"我登录了吗"
   → localStorage 里有没有 token？

   ┌─ 没有 token ─▶ 弹提示"请先登录" → 跳登录页（带上跳回地址）
   │                （登录成功后再跳回来，继续这一步）
   └─ 有 token ────▶ 继续往下

③ 发请求
   fetch('http://localhost:8080/api/items/4/contact', {
     headers: { 'Authorization': 'Bearer eyJhbGci...' }
   })

【网络】
④ 请求穿过网络，到达后端

【后端侧】—— 就是第四章讲的完整旅程
⑤ Gin 查路由表 → 命中 GET /api/items/:id/contact
⑥ 中间件 JWTAuth：验 token 签名、验过期
   → 通过：把 user_id 存进 Context，放行
   → 不通过：返回 401（前端会跳登录页）
⑦ controller.GetContact：从 URL 取出 id=4
⑧ service.GetContact：查这条帖子，取出 contact 字段
⑨ dao：SELECT contact FROM items WHERE id = 4
   （注意：这个查询专门为了拿 contact，平时查询根本不带这个字段）

【返回】
⑩ 后端返回：{"code":0,"message":"ok","data":{"contact":"微信 xiaoming123"}}

【前端侧】
⑪ fetch 拿到响应，api.js 检查 code === 0 ✓
⑫ showContact() 拿到 contact，弹出一个卡片显示
⑬ 用户看到："微信 xiaoming123"
```

**把这条链路画成图**：

```
┌─────────── 浏览器 ───────────┐        ┌────────────── 服务器 ──────────────┐
│                              │        │                                     │
│  ① 点击按钮                  │        │  ⑤ 路由匹配                         │
│  ② 检查 localStorage 有无 token│       │  ⑥ 中间件验 token                   │
│  ③ fetch 发请求 ─────────────┼───HTTP─┼─▶ ⑦ controller 取参数              │
│                              │        │  ⑧ service 取数据                   │
│                              │        │  ⑨ dao 查数据库 → MySQL             │
│  ⑪ 解析响应                  │        │                                     │
│  ⑫ 弹出卡片显示 ◀────────────┼───HTTP─┼── ⑩ 返回 {contact: "微信..."}      │
│  ⑬ 用户看到联系方式          │        │                                     │
└──────────────────────────────┘        └─────────────────────────────────────┘
```

**这个例子里藏着的设计要点**：

| 环节 | 设计 |
|---|---|
| ② 检查登录 | 前端**先拦一道**（体验好，不用白跑一趟网络） |
| ⑥ 中间件 | 后端**再拦一道**（安全底线，前端拦不住的攻击者绕不过这里） |
| ⑨ dao | **专门查询 contact**，列表/详情的查询根本不带它 |
| ⑩ 返回 | 单独一个接口、单独一个响应结构 —— **结构上保证不泄露** |

> **"前端拦一道、后端再拦一道"是标准做法**：
> 前端的校验是**为了体验**（提示更及时），后端的校验是**为了安全**（前端拦不住的人绕不过）。
> **永远不能因为"前端已经校验过了"就省掉后端校验** —— 攻击者可以直接调接口。

## 8.4 前后端怎么保证按同一份"合同"办事

**后端侧：`binding` 标签强制执行**

```go
type CreateItemRequest struct {
    Type     ItemType `json:"type" binding:"required,oneof=lost found"`
    Title    string   `json:"title" binding:"required,max=64"`
    Contact  string   `json:"contact" binding:"required,max=100"`
    // ...
}
```

前端要是不按合同来，后端**直接拒绝**（400），而不是"凑合用"。

**前端侧：照着文档写**

前端开发者拿到 `docs/API接口文档.md`，照着写请求 —— 这就是"按合同办事"。

**如果合同对不上，会发生什么**（第四章实测过的）：

| 情况 | 结果 |
|---|---|
| 字段名大小写写错 | ⚠️ 居然能成功（Go 的 JSON 解析对大小写不敏感，会宽松匹配） |
| 多传了后端不认识的字段 | ✅ 成功，多余字段**被静默忽略** |
| 少传了必填字段 | ❌ **400 报错**：`Field validation for 'Title' failed on the 'required' tag` |
| 传了非法值（如 `type: "xxx"`） | ❌ 400（`oneof` 规则拦下） |

**后端的策略**：能宽容的宽容（大小写、多余字段），**不能让步的绝不让步**（必填、取值范围）。

## 8.5 接口设计的三条经验

看我们的接口设计，有三条值得记住的做法：

**① 用 HTTP 方法和状态码"说人话"**

| 做法 | 好处 |
|---|---|
| 查用 GET、建用 POST、改用 PUT/PATCH、删用 DELETE | 光看请求第一行就知道对方想干嘛 |
| 错误返回真实状态码（401/403/404） | Apifox、监控系统、Nginx 日志都能直接用 |

**② 需要登录的接口单独标注，不要"一刀切"**

```
GET  /api/items          ← 公开：谁都能看列表
GET  /api/items/:id      ← 公开：谁都能看详情
GET  /api/items/:id/contact  ← 要登录：联系方式是隐私
POST /api/items          ← 要登录：得知道是谁发的
```

**"要不要登录"由业务决定，写在路由上**（`middleware.JWTAuth()` 挂在哪条路由上），一眼能看出来。

**③ 敏感字段用"独立接口"隔离，而不是"返回后过滤"**

这是本项目最重要的接口设计。联系方式**不在**列表/详情里返回，
专门做一个 `GET /api/items/:id/contact`。

**为什么不用"查出来再删掉"的方式？**

```go
// ❌ 危险做法：先查全部，再手动删掉敏感字段
item := dao.GetItem(id)
item.Contact = ""          // 手动清空
return item
// 哪天有人加了个新接口，忘了写这行 → 泄露！
```

```go
// ✅ 我们的做法：结构上就不可能有
type Item struct {
    Contact string `json:"-"`    // 序列化时永远跳过，谁写新接口都漏不了
}
```

**"防呆"比"小心"可靠** —— 靠人记住"别忘了删字段"迟早会出事，
靠结构保证"根本拿不到"才万无一失。

---

<details>
<summary><b>参考答案（点开）</b></summary>

**A1** 不是明文，存的是 bcrypt 哈希。
注册时 `utils.HashPassword` 加密后入库；登录时用 `utils.CheckPassword`
把"用户输入的明文"和"库里的哈希"比对。
bcrypt 自带随机盐且计算慢，即使数据库泄露也很难被破解。

**A2** 因为 `models.Item` 的 Contact 字段有 `json:"-"`，序列化时永远被跳过 ——
是**结构上**保证不可能泄露，不是"查出来再删"。
面试官那题的答案：不能。唯一出口是 `/api/items/:id/contact`，
它挂了 JWT 中间件，没 token 返回 401；token 也伪造不了（签名验证）。

**A3** 返回 `400` + `{"code":1007,"message":"状态只能前进，不能回退"}`。
因为 `UpdateStatus` 里用 `statusOrder` 比较序号，新状态必须**严格大于**当前状态。
这么设计是防误操作：手滑点了"已结束"不给改回来，宁可让你重新发一条。
（这也符合 PRD 4.4 的要求）

**A4** 一次查"总数"（`Count`），一次查"当页数据"（`Find` + `Limit/Offset`）。
分页需要 total 才能告诉前端"还有没有下一页"。
如果只查一次、先 `Limit` 再 `Count`，total 可能永远等于 page_size —— 翻页就废了。

**A5** 查不到数据时：
- `var items []models.Item` → JSON 里是 `"list": null`
- `make([]models.Item, 0)` → JSON 里是 `"list": []`

前端的 `data.list.map(...)` 遇到 `null` 会直接崩溃报错。
所以**必须用 `make(..., 0)`**。

**A6** 都是**后端定的**。
`status` 强制为 `searching`（新帖一律从寻找中开始）；
`user_id` 取 token 里解出来的当前登录用户 ID。
如果让前端传 `user_id`，任何人都能冒充别人发帖 —— 这是安全底线。

**A7** 存了 `user_id`、`username`、`exp`（过期时间）、`iat`（签发时间），以及签名。
**不能立刻失效** —— JWT 是无状态的，服务端不留记录。
要"立刻失效"得引入 Redis 黑名单（把作废的 token 存起来，每次请求查一次），
这是本项目的取舍：为了简单，牺牲了"强制下线"的能力。

**A8** 返回 401 之后，**处理函数还会继续执行**。
比如"删除帖子"的接口，中间件发现没登录、返回了 401，
但代码继续跑到 `DeleteItem`，帖子真的被删了 ——
前端看到 401 以为没成功，实际上数据已经没了。**这是严重的安全漏洞。**

**A9** 因为中间件和 controller 是**两个独立的函数**，没有互相调用关系
（中间件是 Gin 调的，controller 也是 Gin 调的），没法直接传参数。
Context（`c`）是它们之间的"传递通道"，而且它**只属于这一次请求**，
不会串到别人的请求里去。

**A10** 因为状态机要求"只能前进不能回退"。
如果编辑接口能改 status，用户 `PUT` 一次就能把"已结束"改回"寻找中"，
`UpdateStatus` 里的校验就白写了。
所以状态变更必须走专门的 `PATCH /api/items/:id/status`。

# 第十一章 部署上线：从本地到服务器

## 11.1 先分清："本地能跑"和"别人能访问"是两回事

前面的章节里，你双击 `lostfound.exe`，浏览器打开 `http://localhost:8080`，一切正常。

但假设你把网址发给同学 —— **他打不开**。

原因在这一行：

```
localhost  =  "我这台电脑"
```

你访问 `localhost:8080`，找的是**你自己电脑**上的 8080 端口。
同学访问 `localhost:8080`，找的是**他自己电脑**的 8080 端口 —— 那里什么都没有。

| | 本地运行 | 线上部署 |
|---|---|---|
| 谁能访问 | 只有你自己 | 任何能上网的人 |
| 地址 | `localhost:8080` | `https://tsx.world/lostfound/` |
| 电脑关机后 | 服务消失 | 服务器 24 小时在线 |
| 用途 | 开发调试 | 作品展示、真实使用 |

"部署"要解决的就是：**把程序放到一台别人能通过网络找到的、永远开机的电脑上。**

## 11.2 部署后的完整架构

我们的部署长这样（每一个方框后面都会讲）：

```
                       https://tsx.world/lostfound/
                                  │
                                  ▼
                     ┌────────────────────────┐
                     │        Nginx           │  ← 门面：管 HTTPS、分路径
                     │  （服务器上的"总台"）     │
                     └───────┬────────┬───────┘
                             │        │
              /lostfound/    │        │   /lostfound/api/
              （静态页面）     │        │   （动态接口）
                             ▼        ▼
                   ┌──────────┐   ┌─────────────────┐
                   │ 前端文件   │   │   Go 服务        │ ← 真正干活的
                   │ web/*.html│   │ 127.0.0.1:8080  │   （systemd 托管）
                   └──────────┘   └────────┬────────┘
                                           │
                                           ▼
                                  ┌─────────────────┐
                                  │   MySQL 数据库   │
                                  │ 127.0.0.1:3306  │
                                  └─────────────────┘
```

注意两个 `127.0.0.1`：Go 服务和 MySQL **都只监听本机**，外网碰不到它们。
外界唯一的入口是 Nginx 的 443 端口 —— 这是安全设计，不是偶然。

## 11.3 第一步：交叉编译 —— 生成"Linux 认识"的程序

**问题**：你在 Windows 上编译出来的 `lostfound.exe`，是给 Windows 看的。
每个操作系统认识的可执行文件格式不同：

| 系统 | 可执行文件格式 | 长什么样 |
|---|---|---|
| Windows | PE | `lostfound.exe` |
| Linux | ELF | `lostfound`（没有 .exe 后缀） |

把 exe 直接传到 Linux 服务器上，它读不懂 —— 就像给只懂中文的人递一份英文合同。

**解法**：Go 语言自带**交叉编译** —— 在 Windows 上，直接编译出 Linux 能跑的程序：

```bash
# 在项目根目录执行（Git Bash / PowerShell 都可以）
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o dist/lostfound_linux_amd64 .
```

三个环境变量，逐个解释：

| 变量 | 值 | 意思 |
|---|---|---|
| `GOOS` | `linux` | 目标操作系统：我要生成 **Linux** 的程序 |
| `GOARCH` | `amd64` | 目标 CPU 架构：64 位 x86 |
| `CGO_ENABLED` | `0` | 不依赖 C 语言库 → 编译出"纯静态"程序 |

`CGO_ENABLED=0` 值得多说一句：Go 默认可能调用系统里的 C 库，
关掉之后产出的程序**自带所有依赖**，扔到任何 Linux 上都能跑，不挑环境。

产物约 34MB —— 看起来大，但里面打包了 Go 运行时 + 所有依赖库（Gin、GORM 等），
**不需要在服务器上装 Go**，也不需要 `go mod download`。

> 一句话总结：这一步产出的是"能在 Linux 上运行的 exe"。

## 11.4 第二步：服务器准备 —— 装数据库、建库、建账号

服务器是一台全新的 Linux（我们的是一台阿里云轻量，Ubuntu 22.04），
上面什么都没有 —— 数据库要先装。

### 装 MySQL

```bash
sudo apt update
sudo apt install -y mysql-server
```

### 小内存机器的调优（重要）

我们的服务器只有 2G 内存，MySQL 默认配置比较"贪"，要让它省着点用：

```ini
# 写入 /etc/mysql/mysql.conf.d/zz-tune.cnf
[mysqld]
innodb_buffer_pool_size = 128M   # 缓存上限：从默认值调小
performance_schema = OFF         # 关掉性能监控表（小站用不上，省内存）
max_connections = 50             # 最大连接数：小站用不了那么多
innodb_log_file_size = 48M
```

改完重启：`sudo systemctl restart mysql`

### 建库 + 建专用账号

```sql
CREATE DATABASE lostfound CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 专用账号：只对这个库有权限，不用 root
CREATE USER 'lostfound'@'localhost' IDENTIFIED BY '你的强密码';
GRANT ALL PRIVILEGES ON lostfound.* TO 'lostfound'@'localhost';
FLUSH PRIVILEGES;
```

**为什么不用 root？** 和"不给客人家里所有房间的钥匙"一个道理：
万一这个账号泄露，损失被限制在 `lostfound` 这一个库里。

> 注意：**不用手动建表**。程序启动时 `AutoMigrate` 会自动按模型建表 —— 见 `main.go` 第 34 行。

## 11.5 第三步：文件就位 + 让程序"常驻"

### 服务器上的目录结构

```
/opt/lostfound/
├── lostfound        ← 交叉编译出来的二进制（要 chmod +x 才能执行）
├── config.yaml      ← 线上配置（数据库密码和 JWT 密钥与本地不同！）
├── web/             ← 前端 6 个页面
└── scripts/         ← seed_data.sh 等运维脚本
```

⚠️ **`config.yaml` 不能提交到 git**（含密码），它在 `.gitignore` 里；
线上的那份是单独准备的，密码、JWT 密钥都和本地不同。

### 为什么不能"直接跑起来就行"

你可能会想：SSH 上去 `./lostfound &` 让它后台跑不就完了？三个问题：

1. **关掉 SSH 窗口，程序就死了** —— 终端挂断时会给程序发信号
2. **服务器重启后，程序不会自己起来**
3. **程序崩溃后，没人把它拉起来**

systemd 一次解决这三个问题。我们写的服务文件：

```ini
# /etc/systemd/system/lostfound.service
[Unit]
Description=LostFound Go backend
After=network.target mysql.service     # 等网络和 MySQL 就绪再启动

[Service]
Type=simple
User=www-data                          # 用低权限用户跑，不用 root
WorkingDirectory=/opt/lostfound        # 程序读 config.yaml 的相对路径基准
ExecStart=/opt/lostfound/lostfound
Restart=always                         # 崩溃自动重启 ← 第 3 个问题的答案
RestartSec=3

[Install]
WantedBy=multi-user.target             # 开机自启 ← 第 2 个问题的答案
```

启用：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now lostfound   # enable=开机自启，--now=立刻启动
```

## 11.6 第四步：Nginx —— 网站的"总台"

服务器上已经有一个 Nginx（tsx.world 主站在用）。我们的项目挂上去，靠**路径**区分：

```
https://tsx.world/            → 主站首页
https://tsx.world/pingpong/   → 乒乓世界
https://tsx.world/lostfound/  → 校园失物招领系统 ← 新加的
```

为什么需要 Nginx 这一层，而不是让 Go 直接对外？

| 职责 | 谁来做 | 为什么 |
|---|---|---|
| HTTPS 加密 | Nginx | 证书只配一处，所有项目共享 |
| 域名 / 路径分发 | Nginx | 一个 443 端口，按路径分给不同项目 |
| 静态文件（html/css/js） | Nginx | 专业选手，比 Go 处理快 |
| 业务逻辑（/api/） | Go 服务 | 只有它懂业务 |

配置片段（加在 443 的 server 块里）：

```nginx
# API 反代：/lostfound/api/xxx → 转发给本机 8080 的 Go 服务
location /lostfound/api/ {
    proxy_pass http://127.0.0.1:8080/api/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# 前端静态文件：Nginx 直接从磁盘拿
location /lostfound/ {
    alias /opt/lostfound/web/;
    index index.html;
}
```

`proxy_pass` 就是"**转发**"：浏览器请求 `tsx.world/lostfound/api/items`，
Nginx 转手把它发给 `127.0.0.1:8080/api/items`，拿到结果再还给浏览器。
对浏览器来说，它自始至终只跟 `tsx.world` 说话 —— **不知道 Go 服务的存在**。

### 关键问题：前端怎么知道后端在哪？

部署后有个隐蔽的坑：前端页面里如果写死 `http://localhost:8080/api`，
在**访问者的浏览器**里，`localhost` 指的是**访问者自己的电脑** —— 直接连不上。

所以 `web/js/api.js` 里做了三场景判断：

```js
const API_BASE = (() => {
  // ① 线上：Nginx 把 /lostfound/api/ 反代给后端
  if (location.hostname === 'tsx.world' || location.hostname === 'www.tsx.world') {
    return '/lostfound/api';
  }
  // ② 本地由后端托管（localhost:8080/app/）：同源，用相对路径
  if (location.port === '8080') return '/api';
  // ③ 本地前端单独打开（file:// 或别的端口）：指向本机后端
  return 'http://localhost:8080/api';
})();
```

同一份代码，在本地和线上都能正确找到后端 —— 这就是"环境自适应"。

## 11.7 日常运维：四个常用命令

部署完不是结束，以后要改代码、看日志、恢复数据。全部在服务器上执行：

```bash
# ① 重启服务（改了配置 / 更新了程序后）
sudo systemctl restart lostfound

# ② 看实时日志（排查问题的第一站）

# ③ 重灌演示数据（排练时数据搞乱了）

```

## 11.8 部署踩过的坑（真实记录）

| 坑 | 现象 | 原因与解法 |
|---|---|---|
| **Nginx 备份文件放错地方** | `nginx -t` 报 duplicate default server | `sites-enabled/` 目录下的**所有文件**都会被加载 —— 备份文件要放到别的目录 |
| **Git Bash 传中文变 GBK** | 库里存成 `Կ�״�` 乱码 | MSYS2 把命令行参数按 CP936 转码；请求体走文件、URL 参数用百分号编码 |
| **空列表返回 null** | 前端 `.map()` 直接崩 | Go 里用 `make([]Item, 0)` 而不是 `var items []Item`，保证返回 `[]` |
| **swap = 0 的风险** | 装 MySQL 时可能 OOM | 加 1G swap 兜底（内存不够时把冷数据挪到硬盘） |

## 11.9 小结

部署 = 把"只有你能访问的程序"变成"所有人都能访问的服务"。三件事：

1. **编译成目标系统能跑的格式** —— 交叉编译（GOOS / GOARCH）
2. **放到服务器上常驻** —— systemd 托管（开机自启 + 崩溃重启）
3. **让流量能找到它** —— Nginx 反代（HTTPS + 路径分发）

做完这三步，你的项目就有了一个**任何人点开就能用的网址**。

# 附录 术语表

| 术语 | 大白话解释 |
|---|---|
| **前端 / 后端** | 前端 = 用户看到、能点的部分；后端 = 在服务器上干活的程序 |
| **HTML** | 网页的**结构**：有哪些东西（标题、按钮、输入框） |
| **CSS** | 网页的**样式**：这些东西长什么样（颜色、大小、位置） |
| **JavaScript（JS）** | 网页的**行为**：用户操作时发生什么（点按钮→发请求） |
| **前后端分离** | 页面文件只写"空壳"，数据由 JS 请求回来再填进去 |
| **fetch** | 浏览器内置的"发 HTTP 请求"函数 |
| **localStorage** | 浏览器里的"本地小仓库"，关掉浏览器再打开数据还在（我们用它存 token） |
| **接口文档 / 契约** | 前后端约定的"菜单"，写清楚要传什么、返回什么 |
| **请求 / 响应** | 你问一句（请求），对方答一句（响应） |
| **HTTP** | 浏览器和服务器说话的"语言规范" |
| **GET / POST / PUT / PATCH / DELETE** | 五种"请求类型"：拿/建/整体改/局部改/删 |
| **状态码** | 响应的结果编号：200 成功、401 没登录、403 没权限、404 找不到 |
| **JSON** | 一种双方约定好的数据格式 |
| **接口 / API** | 一个"功能入口"，比如"发布帖子"是一个接口 |
| **路由** | URL 到处理函数的对照表 |
| **中间件** | 处理请求前先过的"关卡" |
| **token / JWT** | 登录后拿到的"通行证" |
| **鉴权 / 认证** | 确认"你是谁"（Authentication） |
| **授权** | 确认"你能不能干这事"（Authorization） |
| **ORM** | 让你用代码操作数据库、不用手写 SQL 的工具（我们用 GORM） |
| **SQL** | 跟数据库说话的语言 |
| **主键 / ID** | 每条记录的唯一编号 |
| **自增** | ID 自动递增（1、2、3……），不用自己填 |
| **哈希** | 一种"单向加密"，能算出结果但反推不回去 |
| **盐（salt）** | 加密时混进去的随机字符串，让同样的密码算出不同结果 |
| **DSN** | 数据库连接字符串（地址+账号+密码+参数拼成的一串） |
| **迁移 / AutoMigrate** | 让代码自动把数据库表结构建起来 |
| **分页** | 一次只取一部分数据（第几页、每页几条） |
| **LIMIT / OFFSET** | 分页的两个参数：取几条 / 跳过几条 |
| **N+1 问题** | 列表里每一条都单独查一次数据库，导致查询次数爆炸 |
| **闭包** | 能"记住"外部变量的函数 |
| **哨兵错误** | 预定义好的错误值，用来判断"是哪种错" |
